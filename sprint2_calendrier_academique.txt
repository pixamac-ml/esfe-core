SPRINT 2 - BACKEND WORKFLOW CALENDRIER ACADEMIQUE
=================================================

1. RESUME

Le backend JSON du calendrier academique est implemente sans frontend, template ou HTMX.

- CRUD des calendriers et de leurs entrees.
- Workflow strict : brouillon -> valide -> publie -> archive.
- Une seule version publiee par annee academique et annexe ; une nouvelle publication archive l'ancienne.
- Directeur des etudes limite a son annexe ; DG, DG adjoint et Super Admin ont une portee globale.
- Filtres de liste par annexe et annee academique.
- Validation des dates, de la portee programme/classe/semestre et de l'appartenance a l'annexe/annee.
- Refus de publication des periodes qui se chevauchent.
- Les entrees sont publiees/archivees avec leur calendrier.
- Le service de creation des cours verifie les periodes publiees et bloquantes, sans modifier le moteur d'emploi du temps.

4. API/VUES DISPONIBLES

Toutes les reponses sont en JSON sous le prefixe /academics/calendar/.

- GET  /academics/calendar/ : liste ; filtres ?branch=<id>&academic_year=<id>
- POST /academics/calendar/ : creation
- GET  /academics/calendar/<id>/ : detail avec entrees
- PATCH /academics/calendar/<id>/ : modification de version en brouillon
- POST /academics/calendar/<id>/validate/ : validation
- POST /academics/calendar/<id>/publish/ : publication
- POST /academics/calendar/<id>/archive/ : archivage
- POST /academics/calendar/<id>/entries/ : creation d'une entree
- PATCH /academics/calendar/<id>/entries/<entry_id>/ : modification d'une entree
- DELETE /academics/calendar/<id>/entries/<entry_id>/ : suppression d'une entree

Champs de creation calendrier : branch_id, academic_year_id, version (optionnel).
Champs d'entree : title, description, event_type, start_datetime, end_datetime, all_day,
target_scope, programme_id, academic_class_id, semester_id, color, icon, is_blocking, status.
Les dates utilisent ISO 8601 avec timezone.
