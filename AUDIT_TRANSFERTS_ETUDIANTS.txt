# MISSION — AUDIT ET REFONTE MÉTIER DU DASHBOARD SECRÉTAIRE ESFé

Tu travailles sur le projet Django **ESFé Core / Félix Santé**.

Ta mission est d’auditer puis de restructurer profondément le dashboard du rôle **Secrétaire**.

Il ne s’agit PAS de simplement refaire l’interface graphique.

Il faut transformer le dashboard actuel en un véritable **poste de travail numérique quotidien du secrétariat**, adapté au fonctionnement réel d’une école supérieure de santé.

---

# 1. PRINCIPE MÉTIER FONDAMENTAL

Le secrétariat ne doit pas être conçu comme une collection de pages indépendantes.

Il doit être considéré comme :

> **le centre opérationnel de réception, d’enregistrement, de circulation, de transmission et de suivi de l’information administrative de l’établissement.**

La secrétaire doit pouvoir utiliser son dashboard toute la journée pour gérer notamment :

* visiteurs ;
* appels téléphoniques ;
* rendez-vous ;
* courriers entrants ;
* courriers sortants ;
* documents reçus ;
* documents à remettre ;
* transmissions vers les autres services ;
* recherches d’étudiants ;
* réunions ;
* tâches ;
* suivis ;
* rappels ;
* rapports journaliers et périodiques.

Chaque opération importante doit laisser une trace exploitable dans le système.

---

Ne commence pas immédiatement à coder.

Inspecte d’abord entièrement ce qui existe actuellement concernant le rôle Secrétaire.

Analyser notamment :

* `communication` ;

* notifications ;
* documents si un module documentaire existe déjà ;

---

# 3. CE QUI EXISTE DÉJÀ DOIT ÊTRE PRÉSERVÉ

Le projet possède déjà plusieurs briques intéressantes, notamment la notion de registre et différents workflows du secrétariat.

Ne supprime aucune fonctionnalité métier utile uniquement parce que la nouvelle organisation de navigation est différente.

Procéder selon cette logique :

**existant utile → conserver / améliorer**

**existant redondant → fusionner**

**existant mal positionné → déplacer**

**fonctionnalité manquante → ajouter**

**ancienne fonctionnalité devenue inutile → proposer sa suppression avant suppression**

Ne pas casser les données historiques.

Les migrations doivent préserver les données existantes.

---

# 4. VISION DU NOUVEAU DASHBOARD

Le dashboard Secrétaire doit devenir un véritable :

# POSTE DE PILOTAGE DU SECRÉTARIAT

L’écran d’accueil doit répondre immédiatement à trois questions :

1. Que se passe-t-il aujourd’hui ?
2. Qu’est-ce qui attend une action ?
3. Que dois-je faire maintenant ?

Éviter les KPI décoratifs et les cartes inutiles.

Afficher uniquement des informations opérationnelles.

---

# 5. ACCUEIL — « AUJOURD’HUI »

Créer/refondre l’accueil autour de la journée courante.

Exemple :

## Aujourd’hui — Mardi 25 août 2026

Afficher des indicateurs opérationnels tels que :

* visiteurs actuellement présents ;
* rendez-vous du jour ;
* appels nécessitant un rappel ;
* transmissions en attente ;
* documents à remettre ;
* courriers non traités ;
* tâches arrivant à échéance ;
* éventuels éléments urgents ou en retard.

Les compteurs doivent être cliquables et conduire directement aux éléments concernés.

Ne pas surcharger l’interface.

---

# 6. ACTIONS RAPIDES

Les principales opérations quotidiennes doivent être disponibles immédiatement depuis l’accueil.

Prévoir notamment :

* `+ Enregistrer une visite`
* `+ Enregistrer un appel`
* `+ Recevoir un courrier/document`
* `+ Prendre un rendez-vous`
* `+ Nouvelle transmission`
* `Rechercher un étudiant`

Selon l’architecture UI existante, utiliser modal, drawer ou écran rapide.

Objectif :

> une opération courante doit nécessiter le minimum possible de navigation.

---

# 7. REGISTRE NUMÉRIQUE CENTRAL

Étudier très sérieusement le modèle `RegistryEntry` existant.

L’objectif est d’en faire, si son architecture le permet, le **registre numérique central du secrétariat**.

Le registre doit permettre de retracer les événements administratifs importants.

Exemples :

| Heure | Type        | Personne   | Objet                | Destination      | État       |
| ----- | ----------- | ---------- | -------------------- | ---------------- | ---------- |
| 08:12 | Visite      | M. Traoré  | Voir DE              | Direction études | En cours   |
| 08:45 | Courrier    | Ministère  | Courrier officiel    | DG               | Transmis   |
| 09:10 | Appel       | Mme Diallo | Information étudiant | Scolarité        | À rappeler |
| 09:40 | Document    | Aminata    | Attestation          | Secrétariat      | Prêt       |
| 10:15 | Réclamation | Parent     | Paiement             | Gestionnaire     | Transmis   |

Le registre doit permettre :

* filtrage par date ;
* type ;
* personne ;
* destination ;
* statut ;
* priorité ;
* service ;
* recherche textuelle ;
* consultation historique.

Ne pas dupliquer inutilement les données métiers : le registre peut référencer les objets concernés lorsque cela est préférable.

---

# 8. GESTION DES VISITEURS

Le parcours doit être extrêmement rapide.

Lorsqu’une personne arrive :

1. identifier la personne ;
2. saisir son téléphone si nécessaire ;
3. préciser le motif ;
4. éventuellement rechercher l’étudiant concerné ;
5. sélectionner la personne/service demandé ;
6. enregistrer l’heure d’arrivée ;
7. définir l’état ;
8. éventuellement notifier le destinataire.

États possibles à adapter à l’existant :

* attendu ;
* arrivé ;
* en attente ;
* reçu ;
* terminé ;
* annulé.

Prévoir également :

## Personnes actuellement présentes

Exemple :

**M. Coulibaly**
Arrivé 09:24
Attend : Directeur Général
Temps d’attente : 12 min

La secrétaire doit pouvoir immédiatement savoir qui est encore dans l’établissement.

---

# 9. RENDEZ-VOUS + VISITEURS

Ne pas traiter rendez-vous et visiteurs comme deux systèmes complètement isolés.

Lorsqu’une personne ayant un rendez-vous arrive :

`RDV prévu → Arrivé → En attente → Reçu → Terminé`

Prévoir une action :

**Marquer comme arrivé**

depuis le rendez-vous.

La visite correspondante doit pouvoir être créée ou reliée automatiquement.

---

# 10. AJOUTER UN VRAI REGISTRE DES APPELS

Auditer d’abord si une fonctionnalité équivalente existe.

Sinon, créer un système léger de gestion des appels téléphoniques.

Pour chaque appel :

* date ;
* heure ;
* appel entrant/sortant ;
* nom interlocuteur ;
* téléphone ;
* objet ;
* étudiant concerné optionnel ;
* destinataire/service concerné ;
* notes ;
* priorité ;
* demande de rappel ;
* état.

États possibles :

* reçu ;
* message transmis ;
* à rappeler ;
* rappel effectué ;
* traité.

La saisie doit être très rapide.

Exemple :

> Mme Diallo appelle concernant son enfant en L2.
> Elle souhaite parler au DE.

La secrétaire enregistre puis transmet.

Le DE reçoit éventuellement une notification :

> Nouveau message téléphonique transmis par le secrétariat.

---

# 11. TRANSMISSIONS INTERSERVICES

Cette fonctionnalité est fondamentale.

Créer ou consolider un système permettant au secrétariat de transmettre une information ou un dossier vers :

* DG ;
* Directeur des Études ;
* Gestionnaire ;
* Informaticien ;
* Surveillant ;
* autre service autorisé.

Exemple :

Une réclamation financière arrive.

La secrétaire :

1. enregistre la demande ;
2. sélectionne `Gestionnaire` ;
3. transmet.

Le gestionnaire voit :

> Nouvelle transmission du secrétariat
> Réclamation étudiant XXX
> Reçue à 10:42

Le destinataire peut :

* prendre en charge ;
* ajouter éventuellement une observation ;
* marquer comme traité.

La secrétaire doit ensuite voir :

> Traité par Gestionnaire — 11:17

Prévoir des états cohérents, par exemple :

`À transmettre → Transmis → Pris en charge → Traité → Clos`

Adapter aux modèles existants au lieu de créer arbitrairement une nouvelle machine d’état.

---

Chaque transmission doit conserver au minimum :

* priorité ;
* état ;
* personne ayant pris en charge ;

* date de traitement ;
* observations éventuelles.

L’historique ne doit pas être modifiable silencieusement.

# 13. COURRIERS ET DOCUMENTS

Le secrétariat doit devenir une porte d’entrée importante du futur système documentaire.

Prévoir deux grands flux.

## A. COURRIER ENTRANT

Workflow cible :

`Réception → Enregistrement → Numérisation/Pièce jointe → Affectation → Transmission → Traitement → Clôture`

Informations possibles :

* numéro registre ;
* date ;
* expéditeur ;
* organisme ;
* objet ;
* référence ;
* document joint ;
* destinataire ;
* priorité ;
* observations ;
* statut.

## B. COURRIER SORTANT

Workflow :

`Préparation → Validation éventuelle → Signature → Envoi/Remise → Archivage`

Ne pas développer un deuxième moteur documentaire si le projet possède ou prépare déjà un module Documents.

Le secrétariat doit s’intégrer au système documentaire transversal.

* enregistrer l’agent ayant effectué la remise ;
* éventuellement identité de la personne ayant récupéré le document.

# 15. RECHERCHE GLOBALE

Recherche possible sur :

* matricule ;
* téléphone ;
* visiteur ;
* courrier ;
* document ;
* rendez-vous ;

# 17. RAPPORT DE FIN DE JOURNÉE

C’est une fonctionnalité importante.

La secrétaire doit pouvoir obtenir à tout moment un :

# Rapport d’activité du jour

Le rapport doit être généré automatiquement depuis les données du système.

Exemple :

### Activité — 25 août 2026

Visiteurs reçus : 14
Rendez-vous : 7
Appels enregistrés : 11
Appels à rappeler : 2
Courriers reçus : 4
Documents remis : 6
Transmissions créées : 8
Transmissions encore ouvertes : 3

Puis détail des opérations.

Prévoir export :

* PDF ;
* Excel ;
* Word si techniquement pertinent et réellement utile.

Le PDF doit être destiné à la lecture/impression.

Excel doit être destiné à l’exploitation opérationnelle des données.

Word peut être destiné aux rapports administratifs éditables.

---

# 18. CONTINUITÉ DE SERVICE — POINT IMPORTANT

Les exports ne doivent PAS être considérés uniquement comme des rapports statistiques.

Ils doivent également permettre une **continuité minimale du travail en cas d’indisponibilité temporaire de la plateforme ou de connexion Internet**.

Particulièrement pour Excel.

La secrétaire doit pouvoir conserver localement une représentation exploitable de son activité.

Accueil → Recherche étudiant → Créer rendez-vous.

# 35. TESTS

Ajouter des tests sur les workflows critiques.

Minimum :

### Visiteur

création → arrivée → attente → reçu → départ.

### Rendez-vous

création → arrivée → liaison visite → terminé.

### Appel

### Export

### Historique

les anciennes données restent consultables.

# 38. OBJECTIF FINAL

À terme, lorsqu’une secrétaire ouvre son dashboard à 10h30, elle doit pouvoir comprendre en quelques secondes :

> Qui est actuellement présent ?

> Qui attend quelqu’un ?

> Quels rendez-vous arrivent ?

> Qui dois-je rappeler ?

> Quels documents dois-je remettre ?

> Quels courriers sont arrivés ?

> Qu’ai-je transmis ?

> Qu’est-ce qui n’a toujours pas été traité ?

> Qu’est-ce qui est urgent ?

Et lorsqu’elle termine sa journée :

> Qu’ai-je fait aujourd’hui ?

> Qu’est-ce qui reste ouvert ?

> Que dois-je reprendre demain ?

Elle doit pouvoir exporter cette situation en PDF/Excel et conserver un support de continuité opérationnelle.

---

# 39. PRINCIPE DIRECTEUR

Ne cherche pas à donner plus de fonctionnalités à la secrétaire.

Cherche à lui donner :

> **moins d’écrans, moins de navigation, moins de saisies répétitives, mais davantage de contrôle sur son travail quotidien.**

Le dashboard doit devenir un véritable outil métier.

Il ne doit pas ressembler à un panneau d’administration Django amélioré.

Il doit ressembler au **bureau numérique d’une secrétaire d’établissement d’enseignement supérieur**.
