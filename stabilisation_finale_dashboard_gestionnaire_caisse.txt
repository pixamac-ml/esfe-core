3. WORKFLOWS CORRIGÉS
---------------------

Caisse réelle :
- get_branch_cash_balance retourne maintenant le solde signé réel ;
- une caisse négative n'est plus masquée artificiellement à zéro ;
- les alertes financières détectent réellement une caisse négative ;
- une clôture validée ou finale refuse une caisse négative.

Concurrence et atomicité :
- ajout d'un verrouillage de l'annexe avant chaque sortie sensible ;
- les sorties concurrentes sont sérialisées avec select_for_update en production ;
- paiement salaire + mouvement de caisse dans une seule transaction ;
- paiement honoraire + mouvement de caisse dans une seule transaction ;
- avance salaire + mouvement de caisse dans une seule transaction ;
- paiement dépense + mouvement de caisse dans une seule transaction ;
- validation paiement étudiant + mouvement + audit dans une seule transaction ;
- finalisation d'une session cash verrouillée pour empêcher un double encaissement ;
- création de session cash revérifiée sous verrou pour réduire les doublons.

Contrôles de solde :
- dépense refusée si la caisse est insuffisante ;
- salaire refusé si la caisse est insuffisante ;
- honoraire refusé si la caisse est insuffisante ;
- avance refusée si la caisse est insuffisante ;
- sortie manuelle refusée si elle dépasse la caisse disponible ;
- versement bancaire refusé s'il dépasse la caisse disponible.

Intégrité des sources :
- un mouvement saisi manuellement ne peut plus se faire passer pour un paiement,
  un don, une dépense, un salaire, un honoraire, une vente ou un versement bancaire ;
- seules les sources « Manuel » et « Ajustement » sont autorisées dans le formulaire ;
- les références des retraits salaire/honoraires utilisent désormais le cumul payé,
  ce qui évite les références identiques lors de versements répétés du même montant.

Clôture :
- création du brouillon refusée si des opérations orphelines existent ;
- validation et clôture finale refusées si des opérations orphelines existent ;
- correction d'un appel interne erroné vers une fonction inexistante lors du blocage ;
- versement bancaire excessif bloqué avant création ;
- caisse négative bloquée avant validation ou clôture finale.

Boutique et dons :
- validation Boutique déjà atomique et bien reliée à BranchCashMovement : vérifiée ;
- création de don et synchronisation caisse : vérifiées ;
- génération de reçu de don rendue robuste même sans champ receipt_pdf persistant.

8. RISQUES RESTANTS
-------------------

- Les tests isolés utilisent SQLite. Les verrous select_for_update sont conçus pour
  PostgreSQL mais leur comportement concurrent réel doit être confirmé par un test
  de charge sur la base de production ou de préproduction PostgreSQL.
- Si le serveur web expose directement tout MEDIA_ROOT, une URL média connue peut
  contourner Django. En production, les répertoires de reçus, candidatures,
  dépenses et banque doivent rester privés et être servis uniquement via les vues
  contrôlées ou un mécanisme X-Accel/X-Sendfile sécurisé.
- Des opérations historiques déjà orphelines peuvent subsister. Utiliser l'action
  de synchronisation caisse, puis vérifier le rapport avant la première clôture.
- Les justificatifs image de dépense ou banque restent consultables comme fichiers
  métier mais aucun faux bouton PDF n'est créé : seuls les vrais PDF sont proposés
  comme documents PDF dans le dashboard.
