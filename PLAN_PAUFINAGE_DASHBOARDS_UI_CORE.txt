PLAN DE PAUFINAGE COMPLET DES DASHBOARDS ESFE
=============================================

Date : 13 aout 2026
Reference visuelle et structurelle : dashboard certifie du Directeur des etudes
Moule commun : templates/portal/staff/director_dashboard.html


MON AVIS
========

Oui, le constat est juste.

La premiere migration a unifie la coque active : sidebar, topbar, workspace,
loader, drawer, modale, notifications et contexte de role passent maintenant
par le moule certifie du DE.

Mais le contenu interne de plusieurs dashboards reste encore historique :
grands templates monolithiques, CSS local, tableaux ecrits a la main, cartes
KPI dupliquees, filtres non normalises et JavaScript propre a chaque page.

La prochaine phase ne doit donc pas recreer les dashboards. Elle doit migrer
progressivement chaque workspace vers les composants UI Core, tout en gardant :

- les services metier existants ;
- les permissions serveur existantes ;
- le filtrage obligatoire par annexe ;
- les workflows HTMX existants ;
- les regles metier critiques ;
- le meme moule DE pour tous les roles.

La bonne methode est d'avancer dashboard par dashboard, et section par section
pour les plus gros. Chaque dashboard doit etre termine et valide avant de
passer au suivant.


DECISION D'ARCHITECTURE CONFIRMEE
=================================

Finance et Admissions font partie du dashboard Gestionnaire.

Ils ne constituent pas deux dashboards metier autonomes dans l'architecture
cible. Ce sont deux modules du meme workspace operationnel Gestionnaire :

- le Gestionnaire accede a l'ensemble des modules autorises de son annexe ;
- le role Finance entre dans ce meme dashboard avec le module Finance en point
  d'entree et uniquement les capacites financieres qui lui sont accordees ;
- le role Admissions entre dans ce meme dashboard avec le module Admissions en
  point d'entree et uniquement les capacites d'admission qui lui sont accordees.

Les vues et templates finance.html et admissions.html peuvent rester pendant
la migration comme adaptateurs techniques. Ils ne doivent cependant plus faire
evoluer une navigation, un contexte ou une presentation parallele. Leur cible
est de reutiliser le builder, les sections et les composants du Gestionnaire,
puis d'etre reduits a un simple point d'entree ou supprimes lorsqu'aucune URL ne
dependra plus d'eux.

Le contexte effectif depend donc de deux choses distinctes :

- le scope de donnees, principalement l'annexe autorisee ;
- les capabilities du role, qui determinent les modules, donnees et actions
  visibles dans le workspace Gestionnaire.

Le role ne choisit jamais une nouvelle coque. Il ne fait que parametrer le meme
dashboard Gestionnaire a l'interieur du moule certifie DE.


ETAT REEL OBSERVE
=================

Le nombre d'appels de composants ci-dessous ne signifie pas que le dashboard
est vraiment componentise : dans plusieurs cas, presque tous les appels ne
servent qu'a afficher une icone.

1. Famille Gestionnaire
   - environ 1 871 lignes dans le template principal ;
   - 93 appels de composants, dont 91 appels au composant icon ;
   - environ 127 classes CSS historiques dashboard-* ;
   - migration du contenu encore tres partielle ;
   - le point d'entree historique Finance fait environ 748 lignes, avec cartes,
     filtres et tableaux encore ecrits directement dans le template ;
   - le point d'entree historique Admissions fait environ 1 253 lignes, avec
     beaucoup de structure HTML/Tailwind repetee ;
   - ces deux points d'entree doivent converger vers les modules Finance et
     Admissions du Gestionnaire, et non devenir des dashboards autonomes.

2. Secretariat
   - le template principal est deja mince ;
   - il delegue au composant secretary_workspace ;
   - les composants internes restent cependant issus de l'ancien systeme et
     doivent etre alignes sur UI Core.

3. Direction generale
   - environ 1 785 lignes ;
   - 29 appels de composants, tous pour des icones ;
   - environ 155 classes CSS historiques dg-* ;
   - c'est le plus gros chantier visuel avec le Gestionnaire.

4. Informatique
   - environ 706 lignes ;
   - aucun composant dans le template principal ;
   - les modules sont bien separes fonctionnellement, mais pas encore rendus
     avec le vocabulaire UI Core commun.

5. Marketing
   - le template principal est petit, mais il inclut des partials et depend
     encore d'un gros style historique mk-* dans son ancienne base ;
   - aucun composant UI Core dans le template principal.

6. Superadmin
   - environ 455 lignes dans le dashboard principal ;
   - aucun composant UI Core dans ce template ;
   - le contenu repose encore sur les cartes et tableaux de l'ancien layout.

Conclusion de l'audit : le shell est unifie, mais les workspaces ne le sont pas
encore completement. Il faut maintenant normaliser la presentation interne et
absorber Finance et Admissions dans le contexte fonctionnel du Gestionnaire.


OBJECTIF FINAL
==============

Chaque dashboard doit devenir une configuration metier du meme systeme de
composants, et non une nouvelle interface independante.

La chaine cible sera :

  permissions et scope serveur
        -> services/selectors metier filtres par annexe
        -> builder de presentation propre au role
        -> contexte UI normalise
        -> composants UI Core
        -> moule certifie DE

Un template ne devra plus calculer la logique metier. Il devra seulement
assembler des composants a partir d'un contexte deja prepare.


CONTRAT DE CONTEXTE COMMUN
==========================

Chaque dashboard devra fournir, selon ses besoins, les cles normalisees
suivantes :

- dashboard_shell : role, scope, navigation, titres et overlays ;
- page_header : eyebrow, titre, sous-titre et actions autorisees ;
- scope_context : annexe, periode, annee academique et filtres verrouilles ;
- kpis : liste de cartes avec label, valeur, icone, ton, tendance et lien ;
- alerts : alertes autorisees et deja filtrees ;
- tabs : sections ou sous-vues disponibles pour le role ;
- filters : definition des champs, choix, valeurs actives et URL de reset ;
- table : headers, rows, statut, actions, pagination et etat vide ;
- panels : panneaux secondaires et informations contextuelles ;
- quick_actions : uniquement les actions permises cote serveur ;
- capabilities : droits explicites utilises pour afficher ou masquer une action ;
- overlays : contenu et endpoints du drawer, de la modale et de la confirmation ;
- feedback : succes, avertissement, erreur et etat de chargement.

Les querysets Django et les objets sensibles ne devront pas etre transformes
en permissions dans le template. Le builder de presentation recevra seulement
des donnees deja scopees et autorisees.

REGLES DE PERSONNALISATION PAR ROLE
===================================

La personnalisation doit passer par les donnees et les proprietes des
composants, pas par une nouvelle coque HTML.

Chaque role peut adapter :

- le libelle et l'ordre des modules ;
- les KPI visibles ;
- les tons des statuts ;
- les filtres autorises ;
- les colonnes des tableaux ;
- les actions rapides ;
- les endpoints HTMX ;
- le contenu du drawer et de la modale ;
- le niveau de lecture global ou par annexe.

Chaque role ne peut pas adapter :

- la structure generale du shell ;
- la convention de sidebar et topbar ;
- le comportement du loader ;
- la convention des overlays ;
- les regles d'accessibilite ;
- les tokens de couleur, d'espacement et de rayon ;
- les controles serveur de permission et d'annexe.


ORDRE DE REALISATION RECOMMANDE
==============================

L'ordre est volontaire. Le module Finance du Gestionnaire sert de premier
pilote car son workspace historique est plus petit. Les patterns valides seront
ensuite reutilises dans le module Admissions, puis dans les autres contextes.

ETAPE 5 - FINALISATION DU DASHBOARD GESTIONNAIRE
================================================

C'est le chantier metier le plus important. Il doit etre traite en sous-etapes,
sans tenter une reecriture unique des 1 871 lignes. Les modules Finance et
Admissions realises aux etapes 1 et 2 sont deja des parties de ce dashboard ;

5A. Vue globale

- page header et barre de scope ;
- KPI de l'annexe ;
- flux operationnel ;
- alertes et recommandations ;
- actions rapides autorisees.

5B. Consolidation Admissions, inscriptions et paiements

- reutilisation du module Admissions deja migre a l'etape 2 ;
- tables, filtres, statuts, pagination et drawers communs ;
- conservation des endpoints HTMX existants ;
- aucune duplication entre le contexte complet Gestionnaire et le contexte
  restreint du role Admissions.

5C. Salaires staff et honoraires enseignants

- deux sections et deux contextes strictement distincts ;
- salaires auto-generes, jamais crees manuellement ;
- honoraires calcules a partir des heures validees et du tarif ;
- workflow verifier -> corriger -> valider -> payer ;
- confirmations et OTP conserves.

5D. Depenses, caisse et versements bancaires

- filtres et tableaux UI Core ;
- solde de caisse visible ;
- champs banque, reference, date, montant, justificatif et commentaire ;
- alertes de coherence et operations orphelines.

5E. Rapports et cloture mensuelle

- periodes jour, semaine, mois et personnalisee ;
- recettes, depenses, salaires, honoraires, dons et boutique ;
- export Excel et etat financier ;
- cloture sous forme d'archive consultable ;
- aucune suppression de l'historique.

5F. Boutique, dons et compte

- composants de catalogue et de table reutilisables ;
- formulaires dans la modale ou le drawer certifie ;
- espace compte standardise.

Contexte cible : une famille de builders de presentation Gestionnaire par
grande section, avec une couche commune pour le scope, la navigation, les
capabilities, les montants et les statuts. Les roles Gestionnaire, Finance et
Admissions consomment cette meme famille de builders.

Critere de sortie : manager_dashboard.html ne contient plus la logique et le
CSS de onze applications en une seule page. Chaque section est un workspace
compose de composants UI Core et de petits partials metier. Finance et

PHASE SECONDAIRE - COMPOSANTS METIER COMPLEXES
==============================================

La creation de composants qui n'existent pas encore est importante, mais elle
ne doit pas bloquer la migration actuelle des contextes et des composants UI
Core deja disponibles.

Priorite immediate :

- reutiliser les composants generiques existants ;
- adapter correctement les donnees, les capabilities et le scope du role ;
- remplacer les duplications certaines ;
- noter precisement les manques sans inventer trop vite une mauvaise API.

Un petit composant generique manquant pourra etre cree pendant une etape si son
contrat est clair et reutilisable. En revanche, un composant metier complexe
aura son propre audit, son propre prototype et ses propres tests.

Cas prioritaire a traiter plus tard : la maquette de saisie et de calcul des
notes. Elle ne doit pas etre reduite a un simple tableau editable. Son chantier
devra verifier au minimum :

- les regles de calcul, coefficients ou credits et arrondis ;
- les notes absentes, dispensees, rattrapages et corrections ;
- les droits de saisie, de validation, de verrouillage et de publication ;
- l'isolation par annexe, annee, classe, matiere et evaluation ;
- la saisie rapide au clavier, les erreurs par cellule et l'accessibilite ;
- les etats non enregistre, enregistrement, conflit, succes et echec ;
- la recalculation cote serveur et les tests des resultats ;
- l'import eventuel, l'historique des changements et la tracabilite.

Methode pour cette maquette :

1. auditer les composants notes existants et les regles metier reelles ;
2. ecrire les cas de calcul et de permission sous forme de tests ;
3. produire un prototype d'interaction ;
4. definir une API de composant stable ;
5. implementer puis valider sur des donnees representatives.

Cette maquette recevra donc plus de temps dans une phase dediee. Les composants
notes existants ne seront ni supprimes ni recrees a l'aveugle pendant la simple
migration visuelle des dashboards.


METHODE DE TRAVAIL POUR CHAQUE DASHBOARD
========================================

Chaque etape suivra exactement ce cycle :

1. Audit
   - inventorier sections, endpoints, permissions, contextes et CSS ;
   - identifier les donnees globales et celles filtrees par annexe ;
   - relever les tests existants.

2. Contrat de presentation
   - creer ou completer le builder de presentation du role ;
   - normaliser KPI, tableaux, filtres, statuts et actions ;
   - exposer des capabilities explicites.

3. Migration d'une section
   - remplacer le HTML repete par UI Core ;
   - conserver les URLs et actions metier ;
   - utiliser le drawer, la modale et le loader certifies ;
   - enregistrer un composant metier complexe manquant dans le chantier
     secondaire au lieu de bloquer toute la migration.

4. Verification
   - rendu complet et rendu HTMX ;
   - permissions positives et negatives ;
   - test inter-annexes pour les roles locaux ;
   - etats vide, erreur, chargement et donnees volumineuses ;
   - mobile, clavier et accessibilite minimale.

5. Nettoyage
   - retirer uniquement le CSS et le JavaScript devenus inutiles ;
   - ne pas supprimer un ancien bloc avant que tous ses usages soient migres ;
   - documenter le resultat dans le rapport du dashboard.

6. Validation de fin d'etape
   - tests du dashboard ;
   - tests des services metier touches ;
   - python manage.py check ;
   - verification JavaScript ;
   - build Tailwind ;
   - comparaison visuelle des sections critiques.


CRITERES OBLIGATOIRES AVANT DE DECLARER UN DASHBOARD TERMINE
============================================================

- une seule coque certifiee DE ;
- une seule sidebar et une seule topbar ;
- navigation adaptee au role ;
- Finance et Admissions rendus comme modules du Gestionnaire, jamais comme
  nouvelles coques ou interfaces autonomes ;
- scope global ou annexe clairement affiche ;
- aucun acces inter-annexes non autorise ;
- composants UI Core pour layout, KPI, tableaux, statuts, filtres et feedback ;
- aucun tableau generique duplique a la main ;
- aucun nouveau CSS de shell propre au role ;
- aucun calcul metier important dans le template ;
- permissions de chaque action controlees cote serveur ;
- etats vide, chargement, erreur et acces refuse presents ;
- drawer, modale et confirmation du shell utilises ;
- HTMX conserve l'URL, le focus, l'etat actif et les messages ;
- responsive et navigation clavier verifies ;
- tests de rendu, permission et isolation par annexe au vert ;
- CSS historique retire seulement apres preuve qu'il n'est plus utilise.


DECISION RECOMMANDEE
====================

Commencer par le module Finance du dashboard Gestionnaire.

Son point d'entree historique est suffisamment petit pour valider rapidement le
contrat commun du Gestionnaire, les KPI, les filtres, les tableaux, les statuts
et les overlays. Une fois ce module termine, le meme patron sera applique au
module Admissions du Gestionnaire, puis a Secretariat et IT.

Le reste du Gestionnaire et le DG seront traites apres ces pilotes, car leurs
templates sont les plus gros et leurs workflows sont les plus sensibles. Les
roles Gestionnaire, Finance et Admissions partageront le meme workspace, les
memes builders et les memes composants ; seuls le point d'entree, la navigation,
le scope et les capabilities changeront selon l'utilisateur.

Les composants metier complexes encore incomplets seront ensuite travailles
dans une phase dediee. La maquette de saisie et de calcul des notes est
explicitement reservee a ce chantier approfondi afin de ne pas sacrifier les
regles de calcul, les permissions, l'ergonomie ou la tracabilite.

Le travail sera donc fait pas a pas : un meme systeme, un seul moule DE, un
dashboard Gestionnaire contenant Finance et Admissions, puis des contextes de
role precisement adaptes. C'est la bonne suite de la migration actuelle.




# MISSION — FINALISATION DU DASHBOARD GESTIONNAIRE

Nous entrons maintenant dans la phase de finalisation fonctionnelle et visuelle du **dashboard Gestionnaire**.

Le shell global des dashboards est déjà validé et uniformisé.

Le dashboard certifié du **Directeur des Études** constitue désormais le **moule unique de tous les dashboards du système**.

Tu ne dois donc plus créer, reconstruire ou maintenir plusieurs architectures de dashboard.

L’objectif de cette phase est uniquement de **migrer, réorganiser et adapter le contenu métier du Gestionnaire à l’intérieur du shell existant**, en réutilisant au maximum les composants déjà présents dans la bibliothèque UI Core.

---

## 1. RÈGLE D’ARCHITECTURE ABSOLUE

Il n’existe désormais qu’un seul système de dashboard.

Le rôle utilisateur détermine :

* les données accessibles ;
* les modules visibles ;
* la navigation ;
* les KPI ;
* les tableaux ;
* les filtres ;
* les actions ;
* les permissions ;
* le scope d’annexe ;
* les endpoints HTMX accessibles.

Le rôle utilisateur ne doit jamais déterminer :

* une nouvelle sidebar ;
* une nouvelle topbar ;
* un nouveau shell ;
* un nouveau loader ;
* un nouveau système de modal ;
* un nouveau drawer ;
* une architecture HTML indépendante ;
* un nouveau système de notifications.

La coque certifiée du Directeur des Études doit rester l’unique référence.

---

# 2. OBJECTIF DU DASHBOARD GESTIONNAIRE

Le dashboard Gestionnaire représente le workspace opérationnel administratif et financier de l’établissement.

Il doit regrouper notamment :

* vue globale ;
* admissions ;
* inscriptions ;
* paiements ;
* finance ;
* caisse ;
* dépenses ;
* versements bancaires ;
* salaires du personnel ;
* honoraires enseignants ;
* rapports ;
* clôtures mensuelles ;
* boutique ;
* dons ;
* notifications ;
* compte utilisateur.

Ces éléments sont des **modules ou sections du même dashboard Gestionnaire**.

Ils ne doivent pas devenir des dashboards indépendants.

---

# 3. CAS PARTICULIER : FINANCE ET ADMISSIONS

Finance et Admissions doivent être intégrés au dashboard Gestionnaire.

Ils peuvent actuellement posséder :

* leurs anciennes vues ;
* leurs anciennes URLs ;
* leurs anciens templates ;
* certains endpoints historiques.

Ces éléments peuvent rester temporairement comme **adaptateurs techniques** pendant la migration.

En revanche, ils ne doivent plus posséder :

* leur propre shell ;
* leur propre sidebar ;
* leur propre topbar ;
* leur propre langage visuel ;
* leur propre architecture de composants ;
* leur propre CSS de dashboard.

Le rôle `Finance` doit entrer dans le workspace Gestionnaire directement sur le module Finance.

Le rôle `Admissions` doit entrer dans le workspace Gestionnaire directement sur le module Admissions.

Le rôle `Gestionnaire` accède aux modules correspondant à ses permissions.

Ainsi :

```text
Utilisateur
    ↓
permissions + annexe + capabilities
    ↓
workspace Gestionnaire
    ↓
module autorisé
    ↓
UI Core
    ↓
shell certifié Directeur des Études
```

---

# 5. AUCUN RETOUR À L’ANCIEN DESIGN

Pendant cette migration, ne réintroduis pas les anciens éléments uniquement parce qu’ils sont déjà présents dans les templates historiques.

À supprimer progressivement lorsqu’ils ne sont plus utilisés :

* cartes KPI écrites manuellement ;
* tableaux HTML génériques écrits directement dans les pages ;
* anciennes modales ;
* anciens drawers ;
* anciennes sidebars ;
* anciennes topbars ;
* CSS `dashboard-*` ;
* CSS `fin-*` ;
* autres CSS historiques spécifiques au rôle ;

La migration doit aller dans une seule direction :

```text
ancien système
    ↓
UI Core
    ↓
shell DE
```

Jamais l’inverse.

# 7. CONSTRUIRE DES BUILDERS DE PRÉSENTATION

Le template ne doit pas calculer la logique métier.

Préparer les données en Python avant leur rendu.

La chaîne cible est :

```text
permissions serveur
        ↓
scope utilisateur / annexe
        ↓
services ou selectors métier
        ↓
builder de présentation
        ↓
contexte normalisé
        ↓
composants UI Core
        ↓
template
```

Les builders Gestionnaire doivent préparer notamment :

* `manager_workspace_context`
* `manager_navigation`
* `page_header`
* `scope_context`
* `kpis`
* `alerts`
* `tabs`
* `filters`
* `table`
* `panels`
* `quick_actions`
* `capabilities`
* `overlays`
* `feedback`

Ne passe pas au template la responsabilité de déterminer les permissions.

---

# 8. CAPABILITIES EXPLICITES

Les actions visibles doivent être déterminées par le serveur.

Exemples :

```python
capabilities = {
    "can_validate_payment": True,
    "can_edit_payment": False,
    "can_create_expense": True,
    "can_validate_salary": False,
    "can_view_global_finance": False,
}
```

Puis le template consomme uniquement ces droits.

Ne déduis pas une autorisation importante :

* avec JavaScript ;
* à partir d’un bouton visible ;
* à partir du nom du rôle directement dans le template ;
* à partir de données non sécurisées côté client.

---

# 9. ISOLATION PAR ANNEXE

C’est une règle de sécurité obligatoire.

Un Gestionnaire local ne doit jamais obtenir les données d’une autre annexe.

Le filtrage doit être effectué côté serveur.

Cela concerne notamment :

* admissions ;
* inscriptions ;
* étudiants ;
* paiements ;
* caisse ;
* dépenses ;
* salaires ;
* honoraires ;
* boutique ;
* dons ;
* rapports ;
* documents ;
* historiques.

Ne jamais charger toutes les données puis les masquer dans le template.

# 13. RESPONSIVE

Le dashboard doit rester cohérent :

* desktop ;
* laptop ;
* tablette ;
* mobile.

Ne construis pas un deuxième HTML uniquement pour mobile.

Les composants doivent s’adapter grâce au système responsive existant.

# 14. CSS

Interdiction de créer un nouveau gros fichier CSS spécifique au Gestionnaire pour reproduire ce qui existe déjà dans UI Core.

La personnalisation doit passer par :

* les props ;

* les tokens ;

Un CSS spécifique n’est acceptable que pour une nécessité métier réellement exceptionnelle.

# 15. COMPOSANTS MÉTIER

Il est possible qu’une section métier nécessite un composant spécialisé.

Avant d’en créer un :

1. vérifier UI Core ;
2. vérifier les composants métier existants ;
3. vérifier si une composition de composants existants suffit ;
4. vérifier que le concept sera réellement réutilisable.

Ne crée pas un composant métier uniquement pour encapsuler du HTML d’une seule page.

Un composant métier spécialisé doit représenter un véritable concept métier.

# 17. DÉFINITION DE « TERMINÉ »

Une section ne peut être considérée comme terminée que si :

* son contexte est préparé côté Python ;
* ses capabilities sont explicites ;
* le filtrage par annexe est sécurisé côté serveur ;
* ses tableaux sont normalisés ;
* ses statuts sont normalisés ;
