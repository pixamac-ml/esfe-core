RAPPORT DETAILLE — MIGRATION ET ETAT DU DASHBOARD SURVEILLANT GENERAL
=====================================================================

Projet : ESFE Core
Date du rapport : 1er août 2026
Dashboard de référence : Directeur des études (DE)
Dashboard concerné : Surveillant général / position "academic_supervisor"


1. OBJECTIF DE L'INTERVENTION
=============================

L'objectif de cette première intervention n'était pas encore de redéfinir toutes
les attributions métier du Surveillant général. Le travail réalisé a consisté à
remettre son dashboard sur la bonne architecture visuelle et technique, en
prenant le dashboard du Directeur des études comme moule de référence.

Le dashboard DE sert ici de référence pour :

- le shell général de l'application ;
- la sidebar et la topbar ;
- la navigation interne par fragments HTMX ;
- les drawers, confirmations et notifications visuelles ;
- la stabilité des URL ;
- l'organisation entre présentation, navigation et logique métier ;
- le comportement responsive attendu.

Important : reprendre le moule du DE ne signifie pas donner au Surveillant les
mêmes permissions que le DE. Le design et l'architecture sont communs, mais les
attributions métier doivent rester propres à chaque position.


2. SITUATION AVANT LA MIGRATION
===============================

Le dashboard Surveillant utilisait encore une ancienne structure indépendante :

- héritage depuis "base_app.html" au lieu de "portal/app_base.html" ;
- shell spécifique avec les classes historiques "shell", "rail" et "work" ;
- composants spécialisés "supervisor_sidebar", "supervisor_topbar" et
  "supervisor_workspace" ;
- navigation partiellement reconstruite dans les fragments HTMX ;
- coexistence d'URL de dashboard et d'URL de fragments comme pages complètes ;
- redirections historiques utilisant des ancres telles que "#absences" et
  "#courses" ;
- route V2 de la position Surveillant pointant encore vers une route de
  compatibilité intermédiaire ;
- interactions JavaScript propres à cet ancien shell ;
- risque de requêtes non filtrées lorsqu'un Surveillant ne possédait pas
  d'annexe correctement rattachée.

Cette situation pouvait provoquer :

- des changements de design entre deux dashboards ;
- des liens directs ouvrant un fragment sans le shell complet ;
- des retours arrière ou rafraîchissements incohérents ;
- des états actifs de navigation incorrects ;
- des redirections vers des zones qui n'existent plus dans le nouveau design ;
- et surtout un risque de visibilité inter-annexes dans certains cas non
  correctement bornés.


3. MIGRATION DU SHELL VERS UI CORE
==================================

Le template principal suivant a été migré :

  templates/portal/staff/supervisor_dashboard.html

Il utilise maintenant :

- "portal/app_base.html" ;
- "ui_core.app_shell" ;
- "ui_core.app_sidebar" ;
- "ui_core.app_topbar" ;
- "ui_core.page_header" ;
- "ui_core.drawer" ;
- "ui_core.confirm_dialog".

Les éléments concrets ajoutés au shell sont :

- une sidebar UI Core organisée par groupes fonctionnels ;
- une topbar affichant le contexte de l'annexe ;
- un sélecteur de classe actif et responsive ;
- le compteur des notifications non lues ;
- un bouton de déconnexion POST avec jeton CSRF ;
- un indicateur de chargement pour les requêtes HTMX ;
- un workspace unique identifié par "#supervisor-workspace" ;
- un drawer UI Core unique pour les fiches et formulaires secondaires ;
- une boîte de confirmation UI Core pour les actions sensibles.

L'ancienne feuille CSS métier du Surveillant est encore chargée pour préserver
la présentation interne des tableaux, plannings et formulaires qui n'ont pas
encore tous été réécrits en composants UI Core. Le shell, lui, est désormais
celui de la bibliothèque commune.


4. NOUVELLE NAVIGATION DU SURVEILLANT

Une navigation dédiée a été ajoutée dans :

Fonction ajoutée :

Elle construit les groupes suivants :

- Vue générale ;

PRESENCES ET ASSIDUITE

Chaque entrée possède maintenant :

- une cible HTMX commune ;

- un éventuel badge, notamment pour les cas ouverts ;

La fonction a également été exportée depuis :

  ui/services/__init__.py


5. SERVICE DE PRESENTATION AJOUTE
=================================

Un nouveau service a été créé :

  portal/services/supervisor_dashboard_presentation.py

Son rôle est de préparer les données strictement nécessaires au shell UI Core,
sans déplacer la logique métier des services existants.

Il fournit notamment :

- la navigation du Surveillant ;
- la section active ;
- le libellé de l'annexe ;
- l'URL canonique du dashboard ;
- l'URL du fragment actif ;
- l'URL utilisée par le sélecteur de classe ;
- le compteur et l'URL des notifications.

Cette séparation évite de reconstruire des contrats de présentation directement
dans le template principal.


6. CANONICALISATION DES URL ET DES REDIRECTIONS
================================================

L'entrée officielle du dashboard Surveillant est maintenant :

  /portal/dashboard/?section=<section>

Exemples :

  /portal/dashboard/?section=home
  /portal/dashboard/?section=attendance&class_id=12
  /portal/dashboard/?section=schedule&class_id=12
  /portal/dashboard/?section=cases

Les endpoints "workflow" et "cases" sont désormais considérés comme des
endpoints de fragments :

- une requête HTMX reçoit uniquement le contenu du workspace ;
- une requête normale reçue directement sur un endpoint de fragment est
  redirigée vers l'URL canonique du dashboard.

La position "academic_supervisor" a été modifiée dans :

  accounts/position_registry.py

Elle pointe directement vers "accounts_portal:portal_dashboard". Elle ne passe
donc plus par une redirection intermédiaire après connexion lorsque le routage
V2 est activé.

L'ancienne route :

  /portal/supervisor/

est conservée uniquement comme alias de compatibilité pour les anciens favoris
ou liens déjà diffusés. Elle redirige vers l'entrée canonique et n'est plus la
cible principale du registre de position.

Les anciennes redirections d'actions ont aussi été corrigées :

- "#absences" a été remplacé par "?section=attendance" ;
- "#courses" a été remplacé par "?section=courses".

Les boutons et formulaires HTMX modifiés utilisent eux aussi une URL canonique
pour l'historique du navigateur. Cela évite qu'un rafraîchissement ouvre un
fragment isolé ou une ancienne page.


7. ADAPTATEUR JAVASCRIPT UI CORE
================================

Le fichier suivant a été ajouté :

  static/src/js/portal/supervisor_dashboard.js

Il assure les comportements suivants :

- activation visuelle de la bonne entrée de navigation ;
- synchronisation de la classe sélectionnée avec tous les liens concernés ;
- mise à jour de l'URL canonique sans créer une fausse page ;
- synchronisation du sélecteur de classe avec la section active ;
- masquage du sélecteur dans la section des cas disciplinaires ;
- affichage et retrait de l'état de chargement du workspace ;
- ouverture du drawer UI Core avant le chargement de son contenu ;
- fermeture du drawer depuis les anciens événements applicatifs ;
- conversion des confirmations HTMX vers "ui_core.confirm_dialog" ;
- conversion des anciens événements "toast" vers le système ESFE UI ;
- remise au point clavier sur le workspace après un remplacement HTMX.

Le but de cet adaptateur est d'assurer la transition sans casser immédiatement
tous les anciens fragments métier.

9. RENFORCEMENT DU FILTRAGE OBLIGATOIRE PAR ANNEXE
==================================================

Le filtrage par annexe est la règle de sécurité la plus importante de ce
dashboard.

Avant cette intervention, plusieurs vues du Surveillant utilisaient une
résolution d'annexe plus permissive. Lorsqu'aucune annexe n'était trouvée,
certaines fonctions pouvaient construire des querysets trop larges.

Une résolution obligatoire a été introduite dans :

  portal/views/supervisor.py
  portal/views/supervisor_cases.py

Elle s'appuie sur le même mécanisme de portée académique stricte que le DE, en
ajoutant explicitement la position "academic_supervisor" parmi les positions
autorisées et obligatoirement rattachées à une annexe.

Conséquences :

- un Surveillant sans annexe reçoit une interdiction HTTP 403 ;
- le sélecteur de classe reçoit toujours l'annexe du compte ;
- les classes sont recherchées dans cette annexe seulement ;
- les étudiants sont recherchés dans cette annexe et dans la classe active ;
- les enseignants sont recherchés dans cette annexe ;
- les séances, feuilles d'appel et présences sont bornées à l'annexe ;
- les cas étudiants et enseignants sont bornés à l'annexe ;
- les convocations et remplacements sont bornés à l'annexe ;
- les impressions individuelles sont bornées à l'annexe.

Toutes les fonctions principales de "portal/views/supervisor.py" qui utilisaient
l'ancienne résolution ont été basculées vers la résolution obligatoire.

11. ATTRIBUTIONS QUI DOIVENT ETRE REVUES EN PRIORITE
====================================================

Le point le plus important pour la prochaine étape est de décider si les
capacités techniques ci-dessus correspondent réellement à la fonction du
Surveillant général à l'ESFE.

11.1 Validation et réouverture des appels
-----------------------------------------

Question à trancher :

- le Surveillant peut-il ouvrir l'appel uniquement si l'enseignant ne le fait
  pas, ou peut-il toujours le faire ?
- peut-il valider définitivement un appel ?
- peut-il rouvrir seul un appel déjà validé ?
- la réouverture doit-elle exiger un motif obligatoire ?
- le DE doit-il être informé de chaque correction après validation ?
- faut-il conserver un historique avant/après de chaque modification ?

Risque actuel : le pouvoir de rouvrir et de corriger existe techniquement, mais
le niveau d'autorisation et la traçabilité métier doivent être confirmés.

11.2 Présence des enseignants
-----------------------------

Questions à trancher :

- le Surveillant constate-t-il seulement la présence ou valide-t-il une donnée
  ayant un impact administratif ou financier ?
- qui peut corriger une présence enseignant après la journée ?
- un retard doit-il contenir une heure d'arrivée et une justification ?
- une absence doit-elle créer automatiquement une alerte au DE ?
- la présence enseignant doit-elle influencer les honoraires ou seulement
  servir de signal opérationnel ?

Règle à protéger : le dashboard Surveillant ne doit pas devenir un dashboard de
paie ni modifier directement les honoraires enseignants.

11.3 Modification de l'emploi du temps
---------------------------------------

Le Surveillant peut actuellement créer et modifier des créneaux, créer une
séance et matérialiser une semaine ou un mois.

Questions à trancher :

- le Surveillant prépare-t-il un brouillon ou publie-t-il directement ?
- la validation finale appartient-elle au DE ?
- peut-il changer l'enseignant, la matière, la salle et les horaires ?
- peut-il désactiver un créneau déjà utilisé ?
- faut-il une justification pour toute modification d'un planning publié ?
- quelles notifications doivent partir vers l'enseignant, les étudiants et le
  DE après une modification ?

Recommandation : introduire clairement les états "brouillon", "soumis",
"validé/publié", "modifié" et "annulé" si le DE doit garder la validation.

11.4 Cahier de séance
---------------------

Questions à trancher :

- le contenu pédagogique doit-il être saisi uniquement par l'enseignant ?
- le Surveillant doit-il seulement constater qu'il manque ?
- peut-il corriger le contenu ou uniquement demander une correction ?
- doit-il pouvoir renseigner le cahier lorsque l'enseignant est empêché ?
- toute modification par le Surveillant doit-elle être signalée au DE et à
  l'enseignant ?

Risque actuel : le code permet au Surveillant de créer ou modifier le contenu,
le devoir et les observations d'un cahier de séance.

11.5 Affectation des remplaçants
--------------------------------

Questions à trancher :

- le Surveillant peut-il décider seul du remplaçant ?
- doit-il proposer un remplaçant puis attendre l'accord du DE ?
- faut-il vérifier automatiquement les conflits d'horaire et les compétences
  liées à la matière ?
- l'enseignant remplacé, le remplaçant et la classe sont-ils notifiés ?
- faut-il conserver l'identité de l'auteur et la raison du remplacement ?

11.6 Cas disciplinaires
-----------------------

Questions à trancher :

- quelles catégories de cas le Surveillant peut-il créer ?
- peut-il traiter de la même manière un cas étudiant et un cas enseignant ?
- quelles étapes peut-il faire avancer lui-même ?
- à quel niveau la transmission au DE devient-elle obligatoire ?
- peut-il fermer un cas ou seulement le transmettre ?
- quelles notes sont visibles par le DE, l'étudiant, l'enseignant ou le
  secrétariat ?
- faut-il distinguer observation, avertissement, incident grave et sanction ?

11.7 Convocations
-----------------

Questions à trancher :

- le Surveillant peut-il convoquer directement un enseignant ?
- une convocation grave doit-elle être validée par le DE ?
- faut-il une signature, un numéro de document ou un modèle officiel ?
- comment tracer l'envoi, la remise, la lecture et la présence au rendez-vous ?
- les convocations doivent-elles produire un document imprimable archivé ?

11.8 Rapports et impressions
----------------------------

Questions à trancher :

- quels rapports sont seulement consultables ?
- quels rapports peuvent être imprimés ou exportés ?
- quelles données personnelles doivent être masquées ?
- faut-il ajouter des rapports journalier, hebdomadaire et mensuel à transmettre
  au DE ?
- faut-il un journal des exports et impressions sensibles ?

11.9 Alertes et indicateurs
---------------------------

Les seuils doivent être définis avec le métier :

- nombre d'absences déclenchant une alerte ;
- retard enseignant considéré comme anomalie ;
- délai avant qu'un appel non fait soit signalé ;
- durée maximale d'un cas ouvert ;
- niveau de gravité nécessitant une transmission automatique au DE.

11.10 Limites explicites du rôle
--------------------------------

Il faudra écrire noir sur blanc ce que le Surveillant ne peut jamais faire.

Exemples recommandés à confirmer :

- aucun accès inter-annexes ;
- aucune gestion de salaire staff ;
- aucune gestion d'honoraire enseignant ;
- aucune validation financière ;
- aucune modification d'admission ou d'inscription ;
- aucune sanction définitive réservée au DE ou à la Direction ;
- aucune modification du dossier académique permanent sans workflow validé.


12. DETTE TECHNIQUE ENCORE PRESENTE
===================================

La migration du shell est terminée, mais le domaine Surveillant doit encore être
nettoyé techniquement.

12.1 Vue principale trop volumineuse
------------------------------------

  portal/views/supervisor.py

contient encore de nombreuses responsabilités : dashboard, présences, planning,
cours, étudiants, enseignants, remplacements et convocations. Il faudra le
découper en vues ou contrôleurs par domaine, sur le modèle des dashboards les
mieux structurés du projet.

12.2 Templates historiques en double
-------------------------------------

Le dossier des templates contient encore :

- des variantes "sg_*" ;
- des variantes sans préfixe ;
- l'ancienne sidebar ;
- l'ancien en-tête de workspace ;
- d'anciens composants de confirmation.

Ils ont été conservés pour éviter une suppression risquée pendant la migration.
Il faudra identifier ceux qui ne sont plus appelés, les déprécier, puis les
supprimer avec des tests de non-régression.

12.3 CSS métier encore lié à l'ancien design
---------------------------------------------

  static/portal/css/supervisor_dashboard.css

reste nécessaire pour plusieurs panneaux. Une seconde passe devra remplacer
progressivement ses styles de structure par les tokens et composants UI Core,
tout en conservant uniquement les styles réellement propres au planning et aux
tableaux métier.

12.4 Coexistence d'anciens et nouveaux endpoints
------------------------------------------------

Certaines anciennes actions POST restent présentes pour compatibilité avec des
tests ou parcours historiques, alors que les nouveaux panneaux utilisent des
actions HTMX plus fines. Il faudra décider quels endpoints deviennent la source
officielle, migrer tous les consommateurs, puis retirer les doublons.

12.5 Audit et journalisation
----------------------------

Les actions les plus sensibles doivent avoir une stratégie homogène d'audit :

- validation et réouverture d'appel ;
- correction de présence ;
- modification d'emploi du temps ;
- affectation d'un remplaçant ;
- modification d'un cahier de séance ;
- création et progression d'un cas ;
- création d'une convocation.

Il faut vérifier, action par action, si l'auteur, la date, l'ancienne valeur, la
nouvelle valeur, le motif et l'annexe sont enregistrés.

12.6 Validation visuelle manuelle
---------------------------------

Les tests automatisés sont passés, mais une recette manuelle dans un navigateur
reste nécessaire sur :

- ordinateur ;
- tablette ;
- téléphone ;
- sidebar mobile ;
- sélecteur de classe ;
- navigation arrière/avant ;
- drawers et confirmations ;
- impressions ;
- erreurs réseau HTMX ;
- données volumineuses.

- la modification des modèles de données ou l'ajout de migrations.


17. PROCHAINE ETAPE RECOMMANDEE
===============================

La prochaine étape ne devrait pas commencer par ajouter de nouveaux boutons.
Elle devrait commencer par une MATRICE OFFICIELLE DES ATTRIBUTIONS DU
SURVEILLANT GENERAL.

Pour chaque fonction, cette matrice doit indiquer :

- l'objet concerné ;
- ce que le Surveillant peut lire ;
- ce qu'il peut créer ;
- ce qu'il peut modifier ;
- ce qu'il peut valider ;
- ce qu'il peut rouvrir ou annuler ;
- ce qu'il doit transmettre au DE ;
- ce qui exige une justification ;
- ce qui exige une notification ;
- ce qui doit être audité ;
- ce qui lui est strictement interdit.

Ordre de travail recommandé :

ETAPE 1 — Valider les attributions

- appel étudiant ;
- présence enseignant ;
- emploi du temps ;
- remplacement ;
- cahier de séance ;
- discipline ;
- convocation ;
- rapports.

ETAPE 2 — Définir les workflows d'approbation

- actions autonomes du Surveillant ;
- actions soumises au DE ;
- actions réservées au DE ;
- notifications et délais attendus.

ETAPE 3 — Renforcer l'audit et les permissions

- journal avant/après ;
- motif obligatoire ;
- contrôles de statut ;
- verrouillage après validation ;
- tests inter-annexes et tests de permissions négatives.

ETAPE 4 — Refaire les sous-fenêtres métier

- composants UI Core ;
- formulaires homogènes ;
- états vides ;
- erreurs claires ;
- confirmations adaptées au niveau de risque.

ETAPE 5 — Nettoyer l'historique technique

- supprimer les templates inutilisés ;
- retirer les endpoints doublons ;
- découper "portal/views/supervisor.py" ;
- réduire le CSS spécifique ;
- documenter le dashboard final.


18. CONCLUSION
==============

Le dashboard Surveillant est maintenant raccordé au bon moule technique et
visuel : UI Core, navigation stable, URL canonique, fragments HTMX, drawers,
confirmations, notifications et filtrage obligatoire par annexe.

Cette migration règle la base architecturale et met fin à l'ancien shell comme
entrée principale. Elle ne valide cependant pas automatiquement toutes les
attributions actuellement présentes dans le code.

Le principal chantier restant est donc un audit métier approfondi. Les pouvoirs
les plus sensibles à revoir sont la réouverture des appels, la présence des
enseignants, la modification de l'emploi du temps, l'affectation des
remplaçants, la modification du cahier de séance, les cas disciplinaires et les
convocations.

Une fois la matrice d'attributions validée, le dashboard pourra être simplifié,
sécurisé et finalisé sans reproduire les mauvaises redirections ou les anciens
parcours incohérents.

3. NOUVELLE DÉFINITION MÉTIER DU SURVEILLANT

Après validation avec la Direction Générale, le rôle du Surveillant Général est redéfini.

Il ne planifie pas.
