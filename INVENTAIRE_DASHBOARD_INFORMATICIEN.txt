=============================================================

Date : 15/08/2026

But de ce fichier
------------------
Ce document recense les fichiers, URLs, vues, modèles, services, sélecteurs,
fragments, composants et tests qui participent au périmètre du dashboard
Informaticien. Il distingue le dashboard certifié actuellement utilisé des
anciens endpoints encore présents pour compatibilité.

1. POINT D'ENTRÉE ET ACCÈS
--------------------------

Position autorisée : `it_support`

- `accounts/position_registry.py`
  - PositionDefinition `it_support`.
  - URL de destination enregistrée : `accounts_portal:portal_it_v2`.
  - Important : cette URL V2 redirige maintenant vers le dashboard certifié.

- `portal/views/views.py`
  - `portal_dashboard(request)` : route générale des dashboards.
  - Si la position est `it_support`, appelle `_render_it_dashboard(request)`.
  - `_render_it_dashboard(...)` : construit la navigation IT, le contexte et
    rend `portal/informaticien/dashboard.html` dans le shell certifié.
  - `_build_it_dashboard_context(request)` : délègue à
    `portal.services.it_dashboard_service.build_it_dashboard_context`.
  - Anciennes vues de support/comptes : `it_portal`, `it_toggle_account`,
    `it_reset_password`, `it_suspend_account`, `it_reactivate_account`,
    `it_unblock_account`, `it_update_account_email`, `it_diagnostics_panel`,
    `it_accounts_panel`, `it_support_panel`, `it_create_ticket`,
    `it_assign_ticket`, `it_update_ticket_status`, `it_comment_ticket`.

- `portal/views/it_dashboard_v2.py`
  - `it_portal_v2(request)` : compatibilité historique ; redirige vers
    `accounts_portal:portal_dashboard`.

- `accounts/access.py`
  - `get_user_position()` / `get_user_scope()` : décision d'accès globale.

- `accounts/dashboards/helpers.py`
  - `get_user_branch(user)` : annexe du compte connecté.

Règle impérative : toutes les lectures et écritures IT doivent rester filtrées
par l'annexe (`branch` / `annexe`) de l'informaticien connecté.

4. MODÈLES CONCERNÉS
--------------------

Modèles directs (`portal/models.py`) :

- `SupportAuditLog` : trace toutes les opérations IT ; possède `branch`,
  `actor`, `target_user`, `action_type`, `target_label`, `details`, date.
- `SupportTicket` : ticket d'annexe ; états `open`, `in_progress`, `resolved`,
  `rejected`; priorités et catégories ; liens annexe, demandeur, étudiant,
  inscription, assigné, créateur.
- `SupportTicketComment` : commentaire d'un ticket.
- `ArchiveBatch` : archive consultable/restaurable d'une classe ou année.
- `AccountSupportState` : suspension, blocage, mot de passe à changer et
  compteur d'échecs d'un compte.
- `BranchITSettings` : seuil de validation, année active, configuration locale
  de l'annexe.

Modèles académiques consommés :

- `academics.models.AcademicClass` : classe académique.
- `academics.models.Semester` : semestre et état du workflow.
- `academics.models.UE` / `EC` : unités et éléments constitutifs.
- `academics.models.AcademicEnrollment` : inscription académique d'un étudiant.
- `academics.models.ECGrade` : note normale/rattrapage/finale.
- `students.models.Student` : fiche étudiant, carte, inscription.
- Modèle utilisateur Django + `accounts.models.Profile` : rôle/position et
  annexe du personnel.
- `notifier.models.NotificationMessage` : notifications IT.

Tabulator peut également conserver ses fonctions d'export rapide.

Il faut donc distinguer :

```text
Export rapide
→ données de la grille

Export Excel officiel
→ OpenPyXL
```

Si un seul bouton Excel suffit au projet, privilégier la version OpenPyXL officielle si elle est plus propre.

Ne pas créer inutilement deux boutons identiques.

---

# 19. NOMMAGE DES FICHIERS

Les fichiers générés doivent avoir des noms cohérents.

Exemple :

```text
Releve_General_Classe_[classe]_[semestre]_[session].pdf
```

ou :

```text
Releve_Notes_[matricule]_[semestre].pdf
```

Pour Excel :

```text
Notes_[classe]_[semestre]_[session].xlsx
```

Nettoyer les caractères incompatibles dans les noms de fichiers.

---

# 20. PRÉVOIR PLUSIEURS TYPES DE RAPPORTS

Construire une architecture extensible.

Par exemple :

```python
GradeReportService
```

ou réutiliser le service existant.

Il pourrait permettre à terme :

```text
CLASS_GRADE_REPORT
INDIVIDUAL_TRANSCRIPT
RESULTS_REPORT
SESSION_REPORT
RETAKE_REPORT
```

Mais ne créer cette abstraction que si elle s'intègre naturellement à l'architecture actuelle.

Ne pas surarchitecturer inutilement.

---

# 21. DONNÉES OFFICIELLES

Toutes les valeurs du PDF doivent provenir du backend :

* note ;
* moyenne ;
* crédits ;
* statut ;
* validation ;
* décision ;
* étudiant ;
* classe ;
* session ;
* semestre ;
* année académique.

Ne pas reprendre une valeur modifiable du frontend comme source officielle.

---

# 22. PERMISSIONS

Respecter les permissions existantes.

Un utilisateur ne doit pas pouvoir générer un relevé simplement en connaissant une URL.

Vérifier :

* rôle ;
* établissement ;
* annexe ;
* classe ;
* droit de consultation ;
* droit de publication ;
* état des notes.

Réutiliser les permission checks existants.

---

# 23. DOCUMENTS NON ENCORE VALIDÉS

Si les notes ne sont pas encore officiellement validées ou publiées, respecter le workflow existant.

Si nécessaire, afficher dans la prévisualisation :

```text
BROUILLON
```

ou :

```text
NON VALIDÉ
```

mais uniquement si cela correspond déjà aux règles métier du système.

Ne pas inventer une nouvelle règle de publication.

---

# 24. SIGNATURES ET CACHET

Préparer dans le template les zones :

```text
Directeur des Études

Signature

Cachet
```

ou les rôles réels existants.

Ne pas intégrer de fausse signature.

Si le projet possède déjà des signatures électroniques, QR codes ou mécanismes de validation, les réutiliser.

---

# 25. QR CODE / IDENTIFIANT DOCUMENT

Si le projet possède déjà un système de vérification de document, l'intégrer.

Exemple :

```text
Document ID
QR Code
Hash
URL de vérification
```

Mais ne pas créer cela dans cette tâche si aucune architecture de vérification n'existe encore, sauf si c'est très simple et cohérent.

Priorité à l'impression.

# 26. UI DANS LE DASHBOARD

Après finalisation de la saisie :

```text
[ Importer Excel ]

[ Prévisualiser ]

```

ou une organisation similaire cohérente avec la maquette.

Éviter la multiplication de boutons.

On peut aussi avoir :

```text
Actions

  ├── Exporter Excel
  ├── Prévisualiser le relevé
  └── Imprimer
```

si cela s'intègre mieux au design actuel.

# 27. FLOW UTILISATEUR DU RELEVÉ GÉNÉRAL

Je veux exactement un parcours simple :

```text
1. utilisateur saisit les notes avec Tabulator

4. utilisateur clique "Prévisualiser"
5. document officiel s'affiche
6. vérification visuelle
7. utilisateur clique "Imprimer"
8. dialogue d'impression
```

Et éventuellement :

```text
Télécharger PDF
```

# 28. FLOW UTILISATEUR DU RELEVÉ INDIVIDUEL

Depuis une ligne étudiant ou une section dédiée :

```text
Étudiant
   ↓
Relevé individuel
   ↓
Prévisualiser
   ↓
Imprimer / PDF
```

Ne pas obliger l'utilisateur à reconstruire manuellement le contexte.

La classe, session, semestre, année académique, étudiant, etc. doivent être récupérés automatiquement.

# 29. DESIGN

Respecter le design institutionnel existant.

Le document officiel doit être :

* sobre ;
* lisible ;
* administratif ;
* propre ;
* facile à imprimer en noir et blanc ;
* suffisamment compact ;
* sans composants dashboard inutiles.

Les documents officiels ne doivent pas ressembler à une interface SaaS.

Ils doivent ressembler à de vrais documents académiques.

# 30. TABLEAU DU RELEVÉ GÉNÉRAL

Adapter les colonnes dynamiquement au contexte existant.

Exemple seulement :

```text

Matricule
Nom et prénom
CC
TP
Examen
Moyenne
Crédit
Résultat
```

Mais NE PAS coder ces colonnes en dur si la structure académique actuelle permet différents types d'évaluations.

Construire la grille d'impression à partir de la structure réelle.

# 31. GRANDES CLASSES

Tester le relevé général avec :

```text
20 étudiants
50 étudiants
100 étudiants
plus si possible
```

Vérifier :

* pagination ;
* répétition headers ;
* taille texte ;
* lignes ;
* aucune disparition de données ;
* aucune colonne coupée.

---

# 32. TABLEAUX TRÈS LARGES

Si beaucoup de colonnes existent :

* réduire légèrement la taille typographique ;
* passer en paysage ;
* éventuellement A3 ;
* calculer intelligemment la largeur ;
* éviter le débordement hors page.

Ne pas faire simplement :

```css
overflow-x: scroll;
```

pour un document imprimé.

---

# 33. NE PAS IMPRIMER LES INPUTS DE TABULATOR

Le document officiel ne doit pas être une capture de cellules éditables.

Il doit être en lecture seule.

Pas de :

```text
input
select
editor
focus
checkbox d'édition
```

dans le document final.

Ne pas installer si elle existe déjà.
