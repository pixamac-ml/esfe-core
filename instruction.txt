# MISSION — CONSTRUIRE LE VÉRITABLE BACK-OFFICE MÉTIER DU DIRECTEUR GÉNÉRAL
# ESFÉ CORE
# NOUVELLE SESSION CODEX — EXÉCUTION DIRECTE

Tu arrives sur un projet Django existant et fonctionnel : ESFÉ Core.

Ta mission n'est PAS de fabriquer quelques cartes KPI supplémentaires.
Ta mission n'est PAS de refaire le projet.
Ta mission n'est PAS de créer un nouveau design system.
Ta mission n'est PAS de produire un nouvel audit général.

Tu dois construire correctement le dashboard Directeur Général comme un véritable
BACK-OFFICE MÉTIER DE DIRECTION,
alimenté par les DONNÉES RÉELLES du projet.

Le principe fonctionnel à retenir est comparable à Django Admin :

DOMAINE
→ SOUS-SECTION
→ LISTE DE DONNÉES
→ RECHERCHE / FILTRES / TRI / PAGINATION
→ OBJET / DOSSIER / DÉTAIL
→ ACTIONS AUTORISÉES
→ HISTORIQUE / PREUVE lorsque pertinent

mais avec :

- l'UI professionnelle existante d'ESFÉ Core ;
- UI Core ;
- le shell certifié ;
- les permissions DG ;
- le contexte année académique / annexe ;
- HTMX/AJAX/JavaScript existants ;
- une UX beaucoup plus claire que Django Admin.

Le cockpit DG n'est que LA PAGE D'ACCUEIL de ce back-office.

Il ne constitue pas à lui seul le dashboard DG.

4. NE DUPLIQUE PAS LA LOGIQUE MÉTIER
============================================================

Le DG doit consulter les MÊMES données métier que les autres rôles.

Exemple :

si le Gestionnaire utilise déjà un modèle/service pour les paiements,
le DG ne doit pas avoir une deuxième implémentation du calcul des paiements.

Si le Directeur des Études utilise déjà les classes, évaluations et planning,
le DG doit lire les mêmes données avec ses propres permissions et sa propre UX.

Principe :

UNE SOURCE DE VÉRITÉ MÉTIER
+
PLUSIEURS VUES ADAPTÉES AUX RÔLES.

Réutilise les services existants lorsqu'ils sont corrects.

Extrais un service partagé lorsqu'une logique métier est actuellement enfermée
dans une vue et doit légitimement être réutilisée.

Ne copie-colle pas les règles métier.

============================================================
8. UI CORE
============================================================

UI Core est l'autorité visuelle.

Avant de créer un composant :

1. chercher dans UI Core ;
2. réutiliser ce qui existe ;
3. améliorer une primitive existante si nécessaire ;
4. créer une nouvelle primitive uniquement si elle est réellement générique.

Le système de sous-navigation doit idéalement être une primitive UI Core
réutilisable par d'autres dashboards.

Ne crée pas un deuxième design system DG.

Ne réintroduis pas des composants legacy lorsque UI Core possède l'équivalent.

============================================================
19. RECHERCHE
============================================================

La recherche doit interroger réellement les données.

Exemple Étudiants :

?search=camara

→ queryset filtré côté serveur.

Elle doit fonctionner avec HTMX lorsque pertinent pour éviter un reload complet.

Utiliser debounce raisonnable si recherche dynamique.

============================================================
20. FILTRES
============================================================

Les filtres doivent être combinables lorsque pertinent.

Exemple :

Annexe = Bamako
Programme = Médecine
Statut = actif
Recherche = Camara

Le backend construit le queryset correspondant.

Ne crée pas de faux filtres visuels sans effet réel.

============================================================

============================================================
27. CONTRAT DE LOADING
============================================================

Navigation domaine :

→ skeleton/loader workspace uniquement.

Navigation sous-section :

→ loading du contenu de sous-section uniquement.

Recherche/table :

→ loading de la table uniquement.

Bouton :

→ loading du bouton uniquement.

Drawer :

→ skeleton drawer uniquement.

Modal :

→ loader modal uniquement.

Le shell ne doit pas se mettre en loading pour une opération locale.

La sidebar ne doit PAS afficher un spinner si le workspace possède déjà le
loading de cette navigation.
