# MISSION — CORRIGER LE MODULE « EMPLOI DU TEMPS » DU DIRECTEUR DES ÉTUDES

Je veux que tu fasses d’abord un **audit complet de l’implémentation actuelle de l’emploi du temps**, puis que tu corriges son fonctionnement.

Ne fais pas uniquement une correction visuelle ou JavaScript/HTMX.

Le problème semble toucher la **logique métier, le rattachement temporel des créneaux et les requêtes utilisées pour charger une semaine**.

---

# 1. COMPORTEMENT MÉTIER ATTENDU

Le Directeur des Études doit pouvoir suivre ce parcours très simple :

1. Ouvrir **Emploi du temps**.
2. Sélectionner une classe.
3. Arriver sur la grille hebdomadaire de cette classe.
4. Voir uniquement les cours appartenant à la semaine affichée.
5. Ajouter un cours dans un créneau libre.
6. Modifier un cours existant.
7. Supprimer un cours existant.
8. Naviguer vers les semaines précédentes ou suivantes.
9. Revenir à la semaine courante.
10. Imprimer l’emploi du temps de la semaine affichée.

La grille doit donc être une **vue temporelle de données réelles**, et non un planning statique réutilisé artificiellement pour toutes les semaines.

---

# 2. BUG PRINCIPAL À CORRIGER

Exemple concret.

Je consulte :

**Semaine A : 24 au 29 août 2026**

Pour une classe donnée, je programme :

* lundi : Anatomie ;
* mardi : Informatique ;
* mercredi : Physiologie.

Ces cours appartiennent à cette semaine.

Si je navigue ensuite vers :

**Semaine B : 17 au 22 août 2026**

je ne dois absolument pas retrouver automatiquement Anatomie, Informatique et Physiologie simplement parce qu’ils occupent ces positions dans la grille de la semaine suivante.

La semaine du 17 doit charger **ses propres données historiques**.

Donc :

`Classe + semaine/date` doit déterminer les créneaux affichés.

Changer de semaine doit provoquer une véritable nouvelle récupération des données correspondant à cette période.

---

# 3. AUDIT OBLIGATOIRE AVANT MODIFICATION

Avant de coder, inspecte :

* les modèles Django liés au planning ;
* les migrations ;
* les vues ;
* les formulaires ;
* les services éventuels ;
* les URLs ;
* les templates ;
* le JavaScript ;
* les requêtes AJAX/HTMX ;
* les endpoints utilisés par la grille ;
* les paramètres transmis lors du changement de semaine ;
* les filtres ORM utilisés pour récupérer les cours ;
* la logique d’impression.

Détermine précisément comment un créneau est actuellement rattaché :

* à la classe ;
* à l’année académique ;
* au semestre ;
* au jour ;
* à l’heure ;
* à une date réelle ;
* à une semaine.

Je veux notamment savoir si le système stocke actuellement uniquement quelque chose comme :

`classe + lundi + 08:00 + matière`

au lieu de stocker une information permettant de savoir que ce cours appartient réellement au :

`lundi 24 août 2026 à 08:00`.

Si la dimension temporelle est absente ou incorrectement modélisée, corrige l’architecture proprement au lieu de masquer le problème dans le frontend.

---

# 4. LA SEMAINE DOIT ÊTRE UNE VRAIE DIMENSION DU PLANNING

Le système doit pouvoir distinguer sans ambiguïté :

* lundi 17 août 2026 ;
* lundi 24 août 2026 ;
* lundi 31 août 2026.

Ce sont trois journées différentes.

Un cours enregistré le 24 août ne doit donc pas apparaître automatiquement le 17 août.

La navigation :

`Semaine précédente | Aujourd’hui / Cette semaine | Semaine suivante`

doit modifier la période consultée ET les données récupérées.

Le backend doit recevoir explicitement la semaine/date demandée.

Exemple conceptuel :

`?class=<id>&week=2026-08-24`

Puis les requêtes doivent filtrer les créneaux correspondant réellement à cette semaine.

Ne te contente pas de modifier les dates affichées dans le template.

---

# 5. HISTORIQUE DES SEMAINES

Les semaines passées doivent rester consultables.

Exemple :

Aujourd’hui je suis sur la semaine du 24 août.

Je clique sur « semaine précédente ».

Je dois pouvoir retrouver exactement l’emploi du temps enregistré pour la semaine du 17 août.

Je dois également pouvoir avancer vers une semaine future et voir les cours déjà programmés pour cette semaine future.

Le changement de semaine ne doit :

* ni recopier les cours ;
* ni déplacer les cours ;
* ni réutiliser les cours de la semaine courante ;
* ni modifier les données d’une autre semaine.

---

# 6. MODIFICATION D’UN COURS

Lorsqu’un cours existe dans une cellule, le Directeur des Études doit pouvoir l’ouvrir et accéder à une action :

**Modifier**

Il doit pouvoir corriger notamment :

* matière / EC ;
* enseignant ;
* date ;
* heure de début ;
* heure de fin ;
* salle ;
* éventuellement les autres informations déjà prévues dans le projet.

La modification doit concerner **le créneau sélectionné**, pas tous les cours portant le même nom.

Après sauvegarde, la grille doit se rafraîchir correctement.

---

# 7. SUPPRESSION

Ajouter une vraie action :

**Supprimer le cours**

avec confirmation avant suppression.

Exemple :

> Supprimer « Anatomie » du lundi 24 août 2026 de 08h00 à 10h00 ?

Après confirmation :

* supprimer uniquement ce créneau ;
* ne toucher à aucune autre semaine ;
* rafraîchir la grille ;
* conserver une trace d’audit si le projet possède déjà l’infrastructure correspondante.

Vérifie également les permissions : seuls les rôles autorisés doivent pouvoir effectuer cette action.

---

# 8. GESTION DES CONFLITS ET CHEVAUCHEMENTS

Il ne faut pas autoriser silencieusement deux cours incompatibles.

Avant création ou déplacement d’un créneau, vérifier au minimum :

### Conflit de classe

Une classe ne peut pas avoir deux cours qui se chevauchent.

Exemple interdit :

`Anatomie : 08h00–10h00`

et

`Physiologie : 09h00–11h00`

pour la même classe et la même date.

### Conflit enseignant

Si le même enseignant est déjà affecté ailleurs pendant tout ou partie de cette période, empêcher l’enregistrement et expliquer le conflit.

Exemple :

> Impossible de programmer ce cours. M. X enseigne déjà en L2 Santé de 08h00 à 10h00.

### Conflit salle

Si les salles sont gérées dans le système, empêcher également l’utilisation simultanée d’une même salle.

---

# 9. PROPOSER LES CRÉNEAUX LIBRES

Lorsqu’un conflit est détecté, ne te contente pas d’afficher « conflit ».

Si les informations disponibles le permettent, aide le Directeur des Études à identifier les créneaux disponibles.

Exemple :

> Ce créneau est déjà occupé.

Puis éventuellement :

* 10h15–12h15 : disponible
* 14h00–16h00 : disponible

L’objectif est que le système aide réellement à construire l’emploi du temps.

Mais ne crée pas automatiquement un autre créneau sans validation du Directeur des Études.

---

# 10. INTERACTION AVEC LA GRILLE

Pour un créneau existant, prévoir une interaction claire permettant au minimum :

* consulter ;
* modifier ;
* supprimer.

Pour une cellule/créneau libre :

* permettre « Ajouter un cours ».

Évite de multiplier les boutons visibles si cela surcharge la grille.

Un clic sur un cours peut ouvrir un drawer/modal propre contenant le détail et les actions.

L’interface doit rester cohérente avec le design actuel du dashboard.

---

# 11. CLASSE SÉLECTIONNÉE

La classe sélectionnée est essentielle.

Si je consulte :

`L1 Infirmier`

puis semaine du 17 août, je dois obtenir :

`L1 Infirmier + semaine du 17 août`.

Si je passe à la semaine du 24 :

`L1 Infirmier + semaine du 24 août`.

Si je change ensuite pour :

`L2 Infirmier + semaine du 24 août`

le système doit charger les données de cette nouvelle combinaison.

Autrement dit, l’état de la page doit être déterminé au minimum par :

`année académique + annexe + classe + semaine`

et les contraintes temporelles nécessaires.

---

# 12. ANNÉE ACADÉMIQUE

Attention à ne pas mélanger les années académiques.

Les emplois du temps de 2025-2026 doivent rester historiquement accessibles lorsqu’on consulte cette année, mais ne doivent pas contaminer 2026-2027.

Vérifie donc que les requêtes sont correctement rattachées à l’année académique active/consultée.

---

# 13. IMPRESSION

Le bouton Imprimer doit imprimer exactement :

**la classe + la semaine actuellement affichée.**

Si je suis sur :

`L1 Infirmier — semaine du 17 au 22 août 2026`

l’impression ne doit surtout pas récupérer la semaine courante ou une autre semaine.

L’en-tête imprimé doit indiquer clairement la classe et la période.

---

# 14. ATTENTION AUX COURS RÉCURRENTS

Avant de modifier le modèle, vérifie si le projet possède déjà une notion de :

* planning récurrent ;
* modèle hebdomadaire ;
* occurrence de cours ;
* séance réelle.

S'il existe une distinction entre un **modèle hebdomadaire** et les **séances réelles**, conserve cette distinction correctement.

Un modèle peut éventuellement servir à générer une semaine, mais il ne doit pas faire croire que toutes les semaines historiques sont identiques.

Ne détruis pas une architecture existante fonctionnelle sans l’avoir comprise.

---

# 15. TESTS OBLIGATOIRES

Ajoute des tests de régression.

### Test A — isolation des semaines

Créer :

* Classe L1 ;
* Anatomie le 24/08/2026.

Consulter la semaine du 17/08/2026.

Résultat :

**Anatomie ne doit pas apparaître.**

### Test B — retour historique

Créer un cours le 17/08.

Créer un autre cours le 24/08.

Naviguer entre les deux semaines.

Chaque semaine doit afficher uniquement ses propres cours.

### Test C — suppression

Supprimer le cours du 24.

Le cours du 17 doit rester intact.

### Test D — modification

Modifier un cours du 24.

Les autres occurrences/semaines ne doivent pas être modifiées accidentellement.

### Test E — chevauchement classe

Créer 08h–10h.

Tenter 09h–11h pour la même classe/date.

Le système doit refuser.

### Test F — conflit enseignant

Affecter un enseignant à une classe de 08h–10h.

Tenter de l’affecter à une autre classe pendant une période qui chevauche ce créneau.

Le système doit refuser.

### Test G — navigation

Tester :

* semaine précédente ;
* semaine suivante ;
* retour semaine courante.

Les dates ET les données doivent changer ensemble.

### Test H — impression

Vérifier que l’impression utilise la semaine actuellement sélectionnée.

---

# 16. CONTRAINTE IMPORTANTE

Ne corrige surtout pas ce problème en faisant simplement :

* masquer les cours avec JavaScript ;
* changer les labels des dates ;
* dupliquer la grille ;
* vider artificiellement certaines cellules ;
* créer une logique frontend parallèle à la base de données.

La source de vérité doit rester le backend Django et la base de données.

La grille n’est qu’une représentation des données filtrées par période.

---

# 17. MÉTHODE DE TRAVAIL DEMANDÉE

Procède dans cet ordre :

1. auditer l’existant ;
2. identifier précisément la cause du bug ;
3. me donner un résumé court de la cause ;
4. proposer la correction architecturale minimale ;
5. implémenter ;
6. ajouter/corriger les migrations si nécessaire ;
7. corriger backend + frontend ;
8. ajouter les tests de régression ;
9. exécuter les tests ;
10. vérifier manuellement la navigation entre plusieurs semaines ;
11. vérifier modification/suppression/conflits/impression.

Ne réécris pas tout le module si ce n’est pas nécessaire.

Réutilise les composants, conventions, permissions, services et patterns existants du projet.

---

# CRITÈRE FINAL D’ACCEPTATION

Je dois pouvoir prendre une classe et faire ceci :

**Semaine 17–22 août → voir son planning**

→ semaine suivante →

**Semaine 24–29 août → voir un planning différent**

→ modifier Anatomie →

**seul Anatomie du créneau concerné change**

→ supprimer un cours →

**seul ce cours disparaît**

→ essayer de placer un cours sur un horaire occupé →

**le système refuse clairement et permet de rechercher/choisir un créneau libre**

→ revenir à la semaine précédente →

**le planning historique du 17–22 est toujours intact**

→ imprimer →

**seuls la classe et l’emploi du temps de la semaine actuellement affichée sont imprimés.**

Tant que ce scénario complet ne fonctionne pas, considère la fonctionnalité comme non terminée.
