# MISSION UI/UX — DASHBOARD DIRECTEUR GÉNÉRAL ESFé

Le socle backend du dashboard Directeur Général est en cours de stabilisation.

Nous allons maintenant traiter séparément le deuxième axe majeur :

# UI / UX / COMPONENT SYSTEM DU BACK-OFFICE DG

Cette intervention n'est PAS un simple embellissement graphique.

L'objectif est de faire entrer complètement le dashboard DG dans le **Design System commun de la plateforme ESFé**, en prenant comme référence principale le dashboard du **Directeur des Études** et les composants réutilisables déjà présents dans UI Core / la librairie de composants du projet.

Le dashboard DG doit devenir un véritable **back-office exécutif professionnel**, dense, rapide, ergonomique et cohérent avec tous les autres dashboards.

---

# 1. PREMIÈRE RÈGLE — NE PAS INVENTER UN DEUXIÈME DESIGN SYSTEM

Le dashboard DG ne doit PAS avoir :

* son propre système de cartes ;
* ses propres modales ;
* ses propres drawers ;
* ses propres tableaux ;
* ses propres loaders ;
* ses propres badges ;
* ses propres formulaires ;
* son propre système de navigation ;
* son propre CSS massif ;
* son propre JavaScript générique ;

si des composants équivalents existent déjà dans la librairie/UI Core.

Le principe doit être :

```text
UI Core / Component Library
            ↓
      Dashboard DE
            ↓
      Dashboard DG
```

et non :

```text
Dashboard DE → UI Core

Dashboard DG → CSS/HTML/JS spécifique parallèle
```

# 4. SIDEBAR DG — À RECONSTRUIRE FONCTIONNELLEMENT

La sidebar actuelle ne représente pas encore correctement les capacités du Directeur Général.

Elle doit être réorganisée pour devenir la navigation principale d'un véritable back-office administratif.

ATTENTION :

Ne liste PAS chaque modèle Django dans la sidebar.

Regrouper les fonctionnalités en catégories métier cohérentes.

Architecture fonctionnelle cible à étudier :

```text
PILOTAGE
    Vue d'ensemble
    Annexes
    Alertes / suivi

ACADÉMIQUE
    Structure académique
    Classes
    Enseignants
    Planning
    Évaluations
    Résultats
    Passages / réinscriptions

ADMINISTRATION
    Étudiants
    Admissions / inscriptions
    Documents
    Communication

RESSOURCES HUMAINES
    Personnel
    Affectations
    Comptes / accès

FINANCES
    Vue financière
    Paiements
    Caisses / clôtures
    Dépenses
    Salaires / honoraires
    Coupons

DIRECTION & CONTRÔLE
    Validations
    Rapports
    Audit
    Monitoring
```

Cette structure est une CIBLE FONCTIONNELLE, pas une obligation de créer immédiatement toutes les pages.

Comparer avec les fonctionnalités réellement disponibles.

Une entrée ne doit pas être affichée comme pleinement opérationnelle si son écran n'existe pas encore.

---

# 5. SIDEBAR : ERGONOMIE

La sidebar doit gérer proprement les catégories.

Prévoir selon les patterns UI existants :

* groupes ;
* sous-sections ;
* état actif ;
* icônes cohérentes ;
* compteurs lorsque réellement utiles ;
* ouverture/fermeture des groupes ;
* conservation raisonnable de l'état ;
* mode mobile ;
* scroll propre.

Éviter une sidebar de 25 liens plats.

Le DG doit pouvoir comprendre immédiatement :

> Où suis-je ?

> Dans quel domaine ?

> Quelle section est active ?

---

# 6. TOPBAR — ALLÉGER

La topbar actuelle est trop chargée.

Elle doit conserver le même composant/système que le dashboard DE, mais être adaptée intelligemment au DG.

Ne surcharge pas la topbar avec :

* trop de boutons ;
* trop de KPI ;
* trop de texte ;
* tous les filtres possibles ;
* actions secondaires.

La topbar doit principalement contenir les éléments réellement globaux.

---

# 7. CONTEXTE DG DANS LA TOPBAR

Le contexte :

```text
Année académique
+
Annexe / Toutes les annexes
```

est suffisamment important pour rester global.

Il peut donc être intégré à la topbar si cela reste ergonomique.

Exemple conceptuel :

```text
[2026-2027 ▼]   [Toutes les annexes ▼]
```

ou :

```text
Contexte
2026-2027 · Toutes les annexes
[Changer]
```

Trouver la solution la plus cohérente avec les composants existants.

La période :

```text
Aujourd'hui
Semaine
Mois
Trimestre
Année
```

n'a pas nécessairement besoin d'être affichée globalement partout.

Si elle concerne principalement certains écrans analytiques, elle peut rester dans la toolbar de ces écrans.

---

# 8. MOBILE / TABLETTE

Le contexte DG doit TOUJOURS pouvoir être modifié.

Si les selecteurs complets ne tiennent pas dans la topbar :

```text
[Contexte / Filtres]
```

doit ouvrir un drawer ou une modale utilisant le système UI existant.

Jamais :

```text
display: none sur mobile
```

sans solution alternative.

---

# 9. TOOLBAR DE SECTION

Créer/réutiliser un pattern commun pour les sous-sections.

Une section métier peut avoir une toolbar telle que :

```text
[Titre]

[Recherche........................] [Filtres] [Exporter] [+ Action]
```

Mais seulement avec les actions pertinentes.

Cette toolbar doit devenir réutilisable.

Elle peut gérer :

* recherche ;
* filtres ;
* tri ;
* export ;
* action principale ;
* reset des filtres.

Ne duplique pas son HTML dans chaque partial si un composant peut être créé.

---

# 10. RECHERCHE — PRIORITÉ IMPORTANTE

Les sous-sections du DG doivent être pensées pour de gros volumes.

Une recherche purement JavaScript dans les éléments déjà présents dans le DOM n'est pas suffisante.

Pour les listes importantes, utiliser une recherche backend/HTMX.

Exemples :

## Personnel

Recherche :

```text
nom
prénom
matricule/identifiant
fonction
annexe
email
téléphone si disponible
```

## Étudiants

```text
nom
prénom
matricule
classe
formation
annexe
```

## Paiements

```text
référence
étudiant
matricule
type
date
```

## Documents

```text
référence
titre
type
auteur
destinataire
```

selon les données réellement disponibles.

---

# 11. CONTRAT DE RECHERCHE HTMX

Privilégier un pattern uniforme.

Exemple conceptuel :

```html
<input
    type="search"
    name="q"
    hx-get="..."
    hx-trigger="input changed delay:350ms, search"
    hx-target="#results"
    hx-include="..."
>
```

La recherche doit conserver automatiquement :

* année ;
* annexe ;
* filtres de section ;
* pagination pertinente.

Backend :

* sécurisé ;
* scopé ;
* paginé ;
* optimisé.

Ne pas envoyer 5 000 lignes au navigateur pour ensuite les filtrer en JavaScript.

# 15. ACTIONS DE LIGNE

Ne mettre pas cinq gros boutons dans chaque ligne.

Utiliser un menu :

```text
⋮
```

ou le pattern existant.

Exemple Personnel :

```text

Modifier
Changer l'affectation
Suspendre
Réactiver
Révoquer
Voir l'activité
```

Les actions dangereuses doivent être visuellement distinguées.

---

# 16. DRAWERS

Le dashboard DG doit utiliser massivement les drawers lorsque cela améliore le workflow.

Exemple :

```text

```

```text

Fonction
Annexe

```

Puis :

```text

```

Cela permet au DG de travailler sans perdre constamment sa liste et ses filtres.

---

# 17. MODALES

Les actions courtes doivent utiliser les modales communes.

Exemples :

* confirmation ;
* suspendre ;
* réactiver ;
* révoquer ;
* affecter ;
* validation ;
* refus ;
* changement rapide ;
* création légère.

Réutiliser le composant de modale existant.

Si celui-ci ne couvre pas correctement le besoin, l'améliorer au niveau UI Core plutôt que créer `dg_modal_v2`.

---

# 18. DRAWER ≠ MODALE

Utiliser :

## Drawer

Pour :

* consultation ;
* fiche rapide ;
* détails ;
* historique ;
* navigation contextuelle.

## Modal

Pour :

* décision ;
* formulaire court ;
* confirmation ;
* action ciblée.

## Page complète

Pour :

* formulaire complexe ;
* dossier très riche ;
* workflow long ;
* analytics complexes.

Respecter cette distinction.

# 20. GRAPHIQUES

Créer une couche/composant cohérente pour les graphiques.

Le but est d'éviter du JavaScript Chart.js ou équivalent dupliqué dans chaque section.

Prévoir un wrapper/pattern permettant :

* titre ;
* sous-titre ;
* période ;
* état vide ;
* loading ;
* erreur ;
* dataset ;
* légende ;
* responsive.

Exemple conceptuel :

```text
ChartCard
├── header
├── actions/période
├── canvas
├── loading
├── empty
└── error
```

Utiliser la librairie graphique déjà présente si elle existe.

Ne pas ajouter une nouvelle librairie de graphiques sans nécessité.

---

# 21. LES GRAPHIQUES NE DOIVENT PAS ÊTRE DÉCORATIFS

Chaque graphique doit répondre à une question de gestion.

Exemples :


```text

```


# 24. EMPTY STATES

Chaque liste doit avoir un véritable état vide.

Pas simplement :

```text
Aucune donnée
```

si une information plus utile peut être donnée.

Exemple :

```text
Aucun membre du personnel ne correspond aux filtres actuels.

[Réinitialiser les filtres]
```

ou :

```text
Aucune alerte pour cette annexe sur cette période.
```

---

# 25. LOADING STATES

HTMX implique des chargements partiels.

Utiliser un système cohérent.

Éviter :

* spinner dans chaque bouton ;
* trois loaders simultanés ;
* page qui saute ;
* contenu qui disparaît brutalement.

Utiliser les composants/patterns existants.

Une action doit produire un feedback visuel clair.

---

selon le Design System.

Puis mettre à jour uniquement les composants concernés via HTMX lorsque pertinent.

# 28. COMPONENT-FIRST

À partir de maintenant, lorsque plusieurs écrans DG ont besoin du même pattern :

NE PAS copier/coller.

Créer ou réutiliser un composant.

Avant de créer :

```text
Nouveau composant
```

toujours rechercher :

```text
Existe-t-il déjà dans UI Core ?
```

Si oui :

réutiliser.

S'il est presque adapté :

l'étendre proprement.

S'il n'existe réellement pas :

créer un composant générique pouvant être réutilisé ailleurs dans ESFé.

# 30. CSS / JAVASCRIPT INLINE

Ton audit a identifié une quantité importante de CSS/JS inline dans :

```text
templates/portal/dg/dashboard.html
```

Ne fais pas une extraction massive risquée en une seule fois.

Mais à mesure que les composants sont migrés :

* supprimer leur CSS spécifique devenu inutile ;
* déplacer les comportements réutilisables vers les assets/components appropriés ;
* supprimer les handlers dupliqués ;
* conserver uniquement ce qui est réellement spécifique au DG.

Objectif :

réduire progressivement `dashboard.html` à son rôle de composition de page.

---

# 31. DASHBOARD.HTML NE DOIT PAS DEVENIR UNE APPLICATION MONOLITHIQUE

La structure cible doit tendre vers :

```text

      ↓
```

```text

```

* quelques graphiques stratégiques ;

# 34. ACCESSIBILITÉ

# 35. RESPONSIVE DES TABLEAUX

Sur mobile/tablette :

ne pas tenter d'afficher toutes les colonnes.

Identifier :

```text

```

Selon les cas :

* masquer les secondaires ;
* scroll horizontal ;
* drawer de détail ;
* présentation card.

---

# 36. PERFORMANCES UI

Ne pas charger toutes les sections cachées dès l'ouverture.

Examiner le dashboard actuel et convertir lorsque pertinent les grosses sections en chargement à la demande.

Exemple :

```text
DG clique Finance
↓
HTMX charge Finance
```

plutôt que :

```text
Accueil charge Finance + RH + Académique + Audit + Analytics
puis CSS cache 80 % du DOM.
```

Attention néanmoins à ne pas créer une avalanche de requêtes.

Mesurer et choisir intelligemment.

---

# 37. URL ET HISTORIQUE DE NAVIGATION

Lorsque possible, les sous-sections importantes doivent conserver une navigation compréhensible.

Éviter une application où tout dépend d'un état JavaScript invisible impossible à retrouver après refresh.

Respecter les patterns HTMX déjà utilisés dans le projet.

Le refresh d'une page importante ne doit pas ramener arbitrairement le DG ailleurs.
