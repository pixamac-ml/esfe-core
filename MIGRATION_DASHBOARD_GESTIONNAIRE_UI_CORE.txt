DECISION APPLIQUEE
==================

Le dashboard Gestionnaire utilise la coque certifiee du Directeur des etudes :

- ui_core.app_shell ;
- ui_core.app_sidebar ;
- ui_core.app_topbar ;
- ui_core.drawer ;
- ui_core.modal ;
- ui_core.confirm_dialog ;
- loader et comportement communs du shell certifie.

Le contenu Gestionnaire n'a plus le droit de rendre une deuxieme coque. Son
role est uniquement de composer le workspace metier de l'annexe.

Finance et Admissions seront des contextes restreints de ce meme dashboard.
Ils reutiliseront les sections et les composants du Gestionnaire avec une
navigation et des capabilities filtrees cote serveur.


COMPOSANTS DISPONIBLES ET USAGE RETENU
======================================

Structure commune :

- ui_core.page_header : titre et description de la section active ;
- ui_core.page_section : regroupement semantique d'un sous-ensemble ;
- ui_core.content_grid : disposition des zones principales ;
- ui_core.panel : conteneur de formulaire, synthese ou liste secondaire.

Indicateurs et donnees :

- ui_core.stat_card : tous les KPI ;
- ui_core.data_table : tableaux normalises quand les lignes auront un contrat
  de presentation stable ;
- ui_core.status_badge : statuts et compteurs courts ;
- ui_core.progress_bar : avancement d'un processus ;
- ui_core.timeline : historique et activite recente ;
- ui_core.chart_panel : graphiques financiers ;
- ui_core.empty_state : absence de donnees ou de resultat.

Filtres et saisie :

- ui_core.filter_bar : filtres GET et rafraichissement HTMX ;
- ui_core.form_field : enveloppe commune des champs Django ;
- composants forms input, select, date_picker, amount_input et upload_zone
  seulement lorsque leur contrat correspond au formulaire existant.

Feedback et operations :

- ui_core.alert : priorites, anomalies et erreurs ;
- ui_core.loading_overlay : requetes longues ;
- ui_core.toast : confirmation non bloquante ;
- ui_core.drawer : consultation d'un dossier ;
- ui_core.modal : creation ou modification ;
- ui_core.confirm_dialog : validation d'une operation sensible.

DIAGNOSTIC HONNETE ET PLAN DE CRISE - 14 AOUT 2026
===================================================

Ce projet est-il livrable la semaine prochaine ?
-------------------------------------------------

Oui, pour une version operationnelle ciblee et presentee au DG, a condition de
geler immediatement le perimetre. Non, si l'objectif est de terminer toutes les
fonctionnalites ideales, toutes les finitions UX, tous les dashboards de tous
les roles et tous les modules secondaires en meme temps.

Mon estimation sincere est la suivante :

- 3 jours de travail concentre peuvent produire une release candidate du
  parcours critique ;
- 2 jours supplementaires sont necessaires pour les tests, la recette avec le
  DG et les corrections bloquantes ;
- 1 jour de marge est souhaitable pour la migration, les donnees de demo et la
  mise en production.

Cela represente environ 5 a 6 jours ouvrables a temps plein. Ce n'est pas une
garantie : la variable la plus dangereuse n'est plus la quantite de code, mais
la validation sur une base propre, les donnees reelles et les bugs decouverts
pendant la recette.

Faut-il recommencer le projet ?
------------------------------

Non. Recommencer maintenant serait une mauvaise decision strategique :

- le modele de donnees, les migrations, les regles d'annexe, les permissions,
  les workflows paiements, salaires, honoraires, cloture, boutique et dons
  existent deja ;
- les dashboards Finance et Admissions ont deja ete branches sur le workspace
  Gestionnaire et le shell certifie DE ;
- un nouveau projet recreerait les memes risques, mais sans les tests et les
  corrections deja accumules ;
- le vrai probleme est la stabilisation et la priorisation, pas l'absence de
  fondation.

Repartir de zero ne ferait gagner du temps que si le code etait inutilisable.
Les controles Django, les templates actifs et le build CSS passent deja ; ce
n'est donc pas le cas.

Ce qui est deja suffisamment avance
------------------------------------

- shell unique certifie DE et contexte adapte au role ;
- filtrage par annexe et restrictions Finance/Admissions cote serveur ;
- candidatures, inscriptions, paiements et sessions de caisse ;
- salaires staff avec generation automatique et workflow de paiement ;
- honoraires enseignants separes des salaires ;
- depenses, dons, boutique, rapport financier et cloture ;
- exports Excel/PDF, OTP sur correction de paiements et traces financieres ;
- composants UI Core et navigation du workspace Gestionnaire.

Ce qui peut encore bloquer une livraison
-----------------------------------------

P0 - a traiter avant toute demonstration metier :

1. lancer les migrations sur une base de test propre et verifier
   `makemigrations --check --dry-run` ;
2. executer les tests critiques sans processus SQLite concurrent ;
3. tester manuellement les parcours : connexion, annexe, candidature,
   inscription, paiement, caisse, salaire, honoraire, cloture et export ;
4. verifier qu'un utilisateur d'une annexe ne voit jamais les donnees d'une
   autre annexe ;
5. verifier les comptes et donnees de demonstration utilises par le DG ;
6. corriger uniquement les erreurs qui bloquent ces parcours.

P1 - a faire si le temps le permet avant la mise en production :

- message budgétaire explicite avant paiement d'une masse salariale ;
- affichage caisse plus lisible avec solde courant et justificatifs ;
- tests bout en bout OTP, salaire, honoraire et session cash ;
- toasts et confirmations manquants sur quelques actions HTMX ;
- recette de chaque role avec son contexte reel.

P2 - a reporter sans culpabilite :

- maquette complete de saisie/calcul des notes ;
- refonte esthetique approfondie de la boutique ;
- scheduler/cron avance et centre de taches quotidien ;
- dashboard DG d'audit complet ;
- tendances et rapports enrichis ;
- perfectionnement de chaque composant non critique.

Il faut egalement eviter de travailler sur plusieurs dashboards en parallele.
On termine et on teste un parcours, puis on passe au suivant. Le shell unique

Tu n'es pas bloque par un projet a abandonner ; tu es dans une phase de

## Mission : stabiliser et uniformiser définitivement le dashboard Gestionnaire

Nous devons maintenant **finaliser le dashboard Gestionnaire avant de poursuivre les autres dashboards**.

Le dashboard du **Directeur des Études est la référence UI/UX officielle du projet**. Il ne faut pas créer une nouvelle architecture ni réinventer les composants.

### 1. Réutiliser réellement UI Core

Audit le dashboard Gestionnaire actuel et remplace progressivement les anciens fragments, composants locaux, implémentations historiques ou duplications par les composants réutilisables déjà disponibles dans `ui_core`.

Utilise notamment, selon le besoin réel de chaque section :

* `page_header`
* `page_section`
* `content_grid`
* `panel`

* `data_table`

* `timeline`
* `form_field`
* `drawer`
* `modal`
* `confirm_dialog`
* `toast`
* `loading_overlay`
* composants account communs

Ne recrée pas localement un composant qui existe déjà dans UI Core.

### 2. Prendre le Directeur des Études comme référence

Analyse directement le dashboard DE et reproduis **le même contrat d'interface et de navigation**, tout en adaptant évidemment les contenus au métier du Gestionnaire.

Je veux notamment retrouver :

* même shell ;
* même sidebar/topbar ;
* même logique de navigation ;
* même système de sections ;
* même système de sous-sections / tabs ;
* mêmes patterns de tableaux ;
* mêmes filtres ;
* mêmes états vides ;
* mêmes loaders ;
* mêmes feedbacks utilisateur ;
* mêmes drawers ;
* même modal commune ;
* même `confirm_dialog` ;
* même comportement HTMX ;
* même logique responsive.

**Aucun système parallèle spécifique au Gestionnaire ne doit subsister s'il existe déjà un équivalent certifié dans UI Core.**

### 3. Sous-sections

Lorsque certaines sections Gestionnaire contiennent plusieurs fonctions importantes, utilise le système de sous-sections déjà adopté dans le dashboard DE.

Exemple de référence : la section Enseignants du DE avec :

`Vue d'ensemble | Répertoire | Affectations | Dossiers`

Applique cette logique lorsque cela améliore réellement les sections Gestionnaire, sans créer artificiellement des onglets inutiles.

Les sous-sections doivent rester dans le workspace du dashboard et fonctionner proprement avec HTMX lorsque pertinent.

### 4. Tableaux et pagination

Inspecte toutes les listes longues du Gestionnaire.

Utilise le composant `data_table` et ajoute une pagination cohérente avec le standard utilisé dans le dashboard DE lorsque le volume de données le justifie.

Les filtres, recherches et pagination doivent fonctionner ensemble et conserver :

* le scope de l'annexe ;
* les permissions ;
* les paramètres GET ;
* le contexte de la section ;
* les comportements HTMX existants.

Ne charge pas inutilement des centaines de lignes dans une page.

### 5. Modales, drawers et confirmations

Il ne doit plus exister plusieurs systèmes concurrents.

Réutilise exclusivement les composants communs certifiés :

* `drawer` pour la consultation lorsqu'il est approprié ;
* `modal` pour les formulaires/actions qui nécessitent une modale ;
* `confirm_dialog` pour les opérations sensibles.

Supprime uniquement les anciennes implémentations devenues réellement inutiles après vérification de leurs usages.

### 6. Ne pas casser le métier

Cette mission est principalement une **stabilisation UI/UX et architecturale**.

Ne réécris pas inutilement :

* les modèles ;
* les workflows métier ;
* les permissions ;
* le filtrage par annexe ;
* les URLs publiques existantes ;
* les actions HTMX fonctionnelles ;
* les règles Finance/Admissions ;
* les mécanismes OTP ;
* les exports PDF/Excel.

Préserve les fonctionnalités déjà opérationnelles.

### 7. Nettoyage

Identifie les anciens partials/fragments/templates du Gestionnaire qui sont encore utilisés alors qu'UI Core fournit maintenant leur équivalent.

Migre d'abord leurs usages.

Ne supprime un ancien fichier qu'après avoir confirmé qu'il n'est plus référencé nulle part.

Évite toute duplication.

### 8. Validation obligatoire

Après stabilisation :

* `python manage.py check --settings=config.settings_test_local`
* vérification des migrations sans en créer inutilement ;
* compilation/rendu des templates concernés ;

Puis effectue une vérification section par section du dashboard Gestionnaire.

### Résultat attendu

À la fin, je veux pouvoir considérer :

**DASHBOARD GESTIONNAIRE = STABILISÉ ET GELÉ**

Il doit donner l'impression d'appartenir exactement au même produit que le dashboard Directeur des Études.

Commence par auditer l'existant et les composants UI Core disponibles avant de modifier le code. Procède section par section, évite les refontes massives inutiles et termine complètement cette stabilisation avant d'entamer un autre dashboard.

# Mission — Corriger définitivement le layout Sidebar / Main Content des dashboards ESFé Core

Je veux que tu analyses et corriges un problème structurel de layout présent dans les dashboards du projet.

## Constat visuel

Le dashboard utilise une architecture commune avec :

* une sidebar à gauche ;
* une topbar/header ;
* une zone principale de contenu à droite ;
* plusieurs sections/pages dont la hauteur varie fortement.

Le problème apparaît lorsque le contenu principal devient plus haut que la hauteur visible de l’écran.

Sur certaines pages courtes, le dashboard semble correct.

Mais dès qu’une section contient davantage de contenu — par exemple une longue table d’inscriptions, plusieurs cartes, formulaires, graphiques ou composants — la sidebar semble avoir une hauteur limitée/fixe et s’arrête avant la fin du contenu.

Le contenu principal continue ensuite vers le bas tandis que la sidebar est déjà terminée.

Résultat :

* le dashboard paraît coupé verticalement ;
* le fond de la sidebar ne couvre plus toute la hauteur utile ;
* la sidebar et le contenu principal ne restent plus visuellement solidaires ;
* certaines pages donnent l’impression que leur contenu déborde hors du shell principal ;
* le comportement varie selon la quantité de contenu ;
* le rendu n’est pas professionnel.

## Objectif

Je veux une correction **structurelle et globale du layout partagé**, pas un patch page par page.

Le layout doit fonctionner aussi bien avec :

* une page très courte ;
* une page exactement à la hauteur du viewport ;
* une page faisant 2, 3 ou 5 fois la hauteur de l’écran ;
* une grande table paginée ;
* des formulaires longs ;
* des dashboards comportant plusieurs composants ;
* desktop ;
* tablette ;

* le `<main>`;

* les composants Django/Tailwind utilisés pour construire ce shell ;

Recherche particulièrement les classes CSS/Tailwind ou styles équivalents à :

* `h-screen`
* `h-full`
* `min-h-screen`
* `max-h-*`
* `height: 100vh`

* `position: fixed`
* `sticky`
* `absolute`
* `overflow-hidden`
* `overflow-y-auto`
* `overflow-auto`

* `html`

# 2. Vérifier l’architecture de scrolling

# 3. Comportement attendu sur desktop

Sur desktop, je veux un comportement professionnel de type application SaaS/admin moderne.

Conceptuellement :

```text
┌─────────────────────────────────────────────────────────────┐
│ Sidebar        │ Topbar                                     │
│                ├────────────────────────────────────────────┤
│                │                                            │
│                │ Main Content                               │
│                │                                            │
│                │                                            │
│                │ contenu potentiellement très long          │
│                │                                            │
└────────────────┴────────────────────────────────────────────┘
```

Deux architectures sont acceptables si elles sont correctement implémentées :

### Architecture A — Sidebar sticky

La sidebar suit la structure de la page mais reste sticky pendant le scroll.

Exemple conceptuel :

```css
.dashboard-shell {
    min-height: 100vh;
    display: flex;
}

.sidebar {
    position: sticky;
    top: 0;
    height: 100vh;
    flex-shrink: 0;
}

.main-shell {
    flex: 1;
    min-width: 0;
}
```

### Architecture B — Sidebar fixed

La sidebar occupe toujours le viewport et le contenu principal possède l’offset correspondant.

Exemple conceptuel :

```css
.sidebar {
    position: fixed;
    top: 0;
    bottom: 0;
}

.main-shell {
    margin-left: var(--sidebar-width);
}
```

Mais ne choisis pas une architecture uniquement parce que cet exemple est fourni.

Analyse d’abord l’architecture actuelle du projet et conserve la solution la plus cohérente avec le système existant.

---

# 4. Règle fondamentale sur la hauteur

Je ne veux surtout pas quelque chose comme :

```text
dashboard = hauteur fixe 100vh
contenu dépassant = cassure du layout
```

Le shell principal doit avoir au minimum la hauteur du viewport, mais il doit pouvoir grandir naturellement lorsque le contenu grandit.

Autrement dit :

```text
min-height: 100vh
```

peut être pertinent.

Mais une hauteur rigide comme :

```text
height: 100vh
```

sur un mauvais wrapper peut être la cause du problème.

Analyse cela précisément.

Ne remplace pas aveuglément tous les `h-screen` par `min-h-screen`.

Comprends d’abord le rôle de chaque conteneur.

# 5. Sidebar

```text

████████ sidebar
████████ sidebar

         contenu
         contenu
```

* ne pas provoquer de débordement horizontal ;

Vérifie notamment la présence de :

```text

min-w-0
w-full
max-w-*

```

Attention : une table large ne doit pas agrandir le layout entier.

Exemple :

```html

    <table>...</table>

```

et non sur tout le dashboard.

# Clarification des roles, positions et groupes — audit 2026-08-14

## Constat certain

Le Surveillant general possede bien une position officielle en base :
`academic_supervisor`.

Cette position est stockee dans `Profile.position` et recopied dans
`InstitutionalProfile.position`. C'est elle qui permet aujourd'hui l'acces au
dashboard et aux vues de supervision.

En revanche, le champ historique `Profile.role` est incomplet. Il ne contient
que : superadmin, executive, admissions, finance, teacher et student. Il ne
propose ni `academic_supervisor`, ni secretary, ni annex_manager, ni plusieurs
autres postes institutionnels.

Le formulaire de creation RH du DG confirme ce comportement : pour
`academic_supervisor`, il enregistre volontairement `role=""` et
`position="academic_supervisor"`.

Le probleme n'est donc pas une erreur lors de la creation d'un surveillant :
le systeme actuel fonctionne ainsi, mais son architecture d'acces est
incoherente.

## Les trois couches actuelles

1. `Profile.role` : ancien role applicatif general, incomplet et encore
   present dans certaines interfaces d'administration.
2. `Profile.position` / `InstitutionalProfile.position` : fonction metier
   officielle (academic_supervisor, secretary, annex_manager,
   director_of_studies, etc.). C'est la couche qui doit faire autorite.
3. Groupes Django : crees par plusieurs scripts ou manuellement, sans
   synchronisation automatique aux positions. Le registre prevoit un groupe
   `academic_supervisor`, mais les ecrans d'administration ne le creent ni ne
   l'attribuent automatiquement. Un ancien seed cree aussi un groupe nomme
   `Surveillant Academique`, qui n'est pas le nom canonique du registre.

Les permissions sont aujourd'hui reparties entre groupes, positions et
controles directs dans les vues. Cette situation explique pourquoi certains
comptes fonctionnent avec un role vide.

## Architecture a retenir

Ne pas creer une deuxieme copie de toutes les positions dans `Profile.role` :
cela creerait deux sources de verite et de nouvelles divergences.

```text
position institutionnelle = identite metier officielle
position -> groupe Django canonique synchronise automatiquement
groupe -> permissions techniques
vues/services -> controle obligatoire de l'annexe sur chaque lecture et ecriture
```

Exemple :

```text
academic_supervisor
  -> groupe Django : academic_supervisor
  -> permissions de supervision necessaires
  -> annexe obligatoire
  -> aucune visibilite inter-annexes
```

L'administrateur doit choisir une position, pas trois donnees independantes
(`role`, `position`, `groupe`). Le systeme doit ensuite synchroniser le groupe
canonique et les permissions associees.

## Travail a prevoir avant la stabilisation finale de tous les dashboards

1. Definir la matrice officielle position -> groupe -> permissions.
2. Creer les groupes canoniques manquants, dont `academic_supervisor`.
3. Synchroniser automatiquement le groupe lors de la creation ou modification
   d'une position.
4. Migrer et auditer les comptes existants : position valide, groupe coherent,
   annexe presente lorsque le poste est rattache a une annexe.
5. Retirer progressivement `Profile.role` des formulaires d'administration ;
   le conserver uniquement en compatibilite tant que les anciens parcours le
   necessitent.
6. Centraliser les capacites metier par position/groupe, sans jamais remplacer
   le filtrage serveur par annexe.

## Conclusion

Le Surveillant general est un vrai poste metier et son dashboard est reel,
mais son role general et son groupe ne sont pas encore normalises dans le
systeme d'administration. La priorite n'est pas de remplir artificiellement
le champ `role` : il faut finaliser une architecture unique autour de la
position institutionnelle et de groupes canoniques synchronises.

# Principe final

Ne cherche pas à faire rentrer artificiellement tout le contenu dans un seul écran.

Une page administrative peut naturellement être plus haute que le viewport.

Le problème à résoudre est différent :

**quelle que soit la hauteur du contenu, le shell du dashboard doit rester cohérent, la sidebar ne doit jamais sembler se terminer en plein milieu de la page et aucun wrapper ne doit casser visuellement lorsque le contenu grandit.**

Analyse d’abord, trouve la cause racine, corrige le composant partagé, puis teste les dashboards concernés.
