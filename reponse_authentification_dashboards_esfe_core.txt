OBJECTIF FINAL

Faire cohabiter proprement dans le même projet Django :

1. les utilisateurs PUBLIC du site et de la communauté ;
2. les utilisateurs SYSTEM du logiciel scolaire.

Ils peuvent conserver User Django comme noyau technique commun, mais leurs
profils, routes, interfaces, redirections et autorisations doivent être
strictement séparés.

Portal devient la couche centrale d’orchestration des utilisateurs SYSTEM :

Connexion
-> contrôle de l’état du compte
-> contexte d’accès
-> position officielle
-> Portal
-> dashboard principal unique
-> modules HTMX/AJAX/Alpine.js
-> services des applications métier.

Portal ne doit pas absorber tous les modèles et services métier. Il orchestre les
interfaces, la navigation et le routage. Les applications métier conservent leurs
règles, services, modèles et endpoints spécialisés.

========================================================================
1. RÈGLES MÉTIER DÉFINITIVES
========================================================================

A. PUBLIC

Un utilisateur PUBLIC :

- utilise le site public et la communauté ;
- possède un profil public ;
- peut gérer ses informations communautaires ;
- ne possède aucune position institutionnelle ;
- n’accède à aucun dashboard SYSTEM ;
- ne reçoit aucun accès logiciel par simple inscription.

B. SYSTEM

Un utilisateur SYSTEM :

- possède un profil institutionnel ;
- possède une position principale officielle ;
- possède une catégorie dérivée de sa position ;
- possède une portée organisationnelle ;
- possède une annexe lorsque son scope est BRANCH ;
- possède un dashboard principal unique ;
- reçoit ses capacités grâce aux permissions Django.

Son profil professionnel, ses paramètres et son changement de mot de passe
restent dans son dashboard Portal. Il ne doit jamais être redirigé vers le profil
communautaire pendant son travail.

C. CATÉGORIES

Les catégories sont dérivées du registre des positions :

- STUDENT ;
- TEACHING_STAFF ;
- ADMIN_STAFF.

Elles ne doivent pas être saisies indépendamment.

D. ANNEX_MANAGER

La gestionnaire possède une seule position officielle :

- position : ANNEX_MANAGER ;
- libellé : Gestionnaire d’annexe ;
- catégorie : ADMIN_STAFF ;
- scope : BRANCH ;
- annexe obligatoire ;
- dashboard principal unique dans Portal ;
- groupe de capacités par défaut : annex_manager.

Les anciens concepts gestionnaire, manager, branch_manager et certains usages de
finance_manager doivent être normalisés lorsqu’ils représentent réellement cette
même fonction.

Le dashboard Portal de la gestionnaire doit réunir les fonctions existantes :

- candidatures et dossiers ;
- inscriptions ;
- encaissements et paiements ;
- caisse ;
- dépenses ;
- salaires ;
- avances ;
- honoraires des enseignants ;
- boutique et stocks ;
- dons ;
- clôtures mensuelles ;
- versements en banque ;
- rapports et exports ;
- situation financière de l’annexe.

Ne réécris pas les règles métier déjà fonctionnelles. Réutilise les services et
endpoints fiables de accounts, payments, shop et des autres applications.

E. PAYMENT AGENT

PaymentAgent représente par défaut une affectation ou une capacité opérationnelle,
pas une identité donnant automatiquement accès à un dashboard complet.

Il peut recevoir des permissions limitées pour :

- encaisser ;
- gérer une session de caisse ;
- émettre un reçu ;
- consulter les opérations autorisées.

S’il existe des comptes exerçant exclusivement cette fonction, conserve
temporairement leur position et fournis-leur une expérience restreinte. Ne les
convertis pas automatiquement en ANNEX_MANAGER.

F. AUTRES POSITIONS

- STUDENT : STUDENT, scope BRANCH, dashboard étudiant Portal ;
- TEACHER : TEACHING_STAFF, scope BRANCH, dashboard enseignant Portal ;
- SECRETARY : ADMIN_STAFF, scope BRANCH, dashboard secrétaire ;
- ADMISSIONS_OFFICER : ADMIN_STAFF, scope BRANCH par défaut ;
- ACADEMIC_SUPERVISOR : ADMIN_STAFF, scope BRANCH ;
- IT_SUPPORT : ADMIN_STAFF, scope BRANCH ;
- DIRECTOR_OF_STUDIES : ADMIN_STAFF, scope BRANCH par défaut ;
- MARKETING_MANAGER : ADMIN_STAFF, scope GLOBAL avec ciblage par annexe ;
- EXECUTIVE_DIRECTOR : ADMIN_STAFF, scope GLOBAL ;
- DEPUTY_EXECUTIVE_DIRECTOR : ADMIN_STAFF, scope GLOBAL ;
- SUPER_ADMIN : ADMIN_STAFF, scope GLOBAL.

Une supervision exceptionnelle de plusieurs annexes doit passer par une
affectation explicite, jamais par un groupe ou un alias.

G. DJANGO

- User reste le noyau d’authentification ;
- is_active contrôle l’utilisation administrative du compte ;
- is_staff signifie uniquement accès à l’administration Django ;
- is_superuser reste un privilège technique exceptionnel ;
- SUPER_ADMIN est une fonction métier et n’implique pas automatiquement
  is_superuser ;
- les groupes sont des ensembles de permissions ;
- les groupes ne déterminent jamais la position ni le dashboard.

- PUBLIC ne peut atteindre aucune ressource SYSTEM ;

- données publiques, académiques, RH et financières préservées ;
- routes historiques sécurisées ou redirigées ;
